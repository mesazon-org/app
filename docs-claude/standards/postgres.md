# PostgreSQL schema

Project-agnostic rules. Other owners: [Mesazon schema](../features/flow/03-schema.md), [repository](../features/flow/04-repository.md), [Doobie](doobie.md), [newtypes](iron.md), [Scala](scala.md).

## Layout and migrations

Schema module:

- `migrations/V<version>__<name>.sql`: deployed schema, applied in version order.
- Local bootstrap: one-shot schema/roles/grants setup; not a migration and never assumed in deployment.
- Local migration config: connection + strict filename validation.
- Deployment package/job: migrations only, schema-scoped. `clean`/wipe is dev/disposable-only.

Provision new DB roles/grants in local bootstrap and separately in deployed environments; migrations must not depend on local-only roles.

Migration rules:

- `V<version>__<snake_case_description>.sql`; use sortable versions (e.g. `YYYY.MM.DD`, same-day `.1`, `.2`) and strict naming validation.
- One append-only migration per change set. Never edit a migration already applied to a deployed environment; add a later version.
- Keep one DDL style (e.g. lowercase keywords).

## Names and types

- Table: singular `snake_case`, `{{owner}}_{{entity}}`; child/join tables retain owner. Use `user_details`, `organization_user`; not `users`, `user`, `customer_book`.
- Column: spelled-out `snake_case`.
- ID column: `{{entity}}_id uuid`; application-generated, no DB default.
- String: `text`, never `varchar(n)`; domain/refined types enforce format/length.
- Time: `timestamptz`, never unzoned `timestamp`.
- Enum: `text` holding code enum case name; native PG enum only as a documented exception.
- Multi-part value: separate columns mirroring its domain fields. Small multi-valued records read/written atomically and never queried independently may use one `jsonb` column.
- `not null` by default; nullable iff the row field is optional. Mismatch is a runtime decode failure.
- Nearly every table ends with `created_at`, `updated_at` as `timestamptz not null`; application clock sets both and refreshes `updated_at`. No trigger/`default now()`. Add expiry/activity timestamps as needed.

## Keys, constraints, indexes

- Declare PK at table end; composite for joins.
- Use single/composite `unique (...)`. If code maps its violation distinctly, name it; otherwise anonymous may map generically.
- Explicit FK to parent key. Add a supporting index when queried by the FK.
- Index: `idx_<table>_<purpose>`. Hash for single-column equality; b-tree with explicit order/`DESC` for ranges/order.
- Caller-facing unique constraint/index: stable explicit `uq_<table>_<distinguishing_columns>`. Code matches the driver-reported constraint for unique-violation SQL state. Rename code and constraint together. Never match an autogenerated/truncated name (Postgres limit: 63 chars).

## Historical data

- Parent owning financial/audit history: soft-delete via application-set lifecycle enum (`ACTIVE`/`ARCHIVED` style), no DB default; active-only reads by default. Pure children with no history may hard-delete.
- Historical rows: append-only; cancellation/refund/reversal changes status, never deletes.
- Snapshot relevant parent fields onto history in addition to FK.
- History→parent FK: `on delete restrict`, never cascade.
- Erasure anonymizes identifying snapshots while retaining the financial/audit row.

## Discriminated subtypes

For mutually exclusive subtypes sharing identity/downstream targets:

- One table + `<entity>_type text not null`; subtype-specific fields are nullable columns on it.
- Sub-record belonging to one subtype but not itself the entity: tenant-scoped child table `(tenant_id, parent_id, own_id)` with tenant-scoped FK. Service paths may enforce allowed parent subtype.
- Active uniqueness includes tenant + subtype and uses a partial active-only index.
- Discriminator is the sole subtype truth; typed reads/updates filter it and wrong-type lookup is not found.
- Archiving parent retains children; a history-free child may delete.
- Never model extensible kinds with `is_<kind>` booleans or duplicate identity across subtype tables.

## Schema/code lockstep

- Rename/change SQL names and every literal code/config reference together.
- Row field order = shared query column-list order = schema column order; positional codecs make mismatch a silent/runtime bug. Reuse one column-list fragment across `SELECT`/`INSERT`/`RETURNING`; see [Doobie](doobie.md#reusable-field-list--positional-row-codec).
- Schema/table identifiers come from one config model, never query literals. Update every duplicated environment/test config.

## Testing

- Shared DB harness: table-existence check, truncation, arbitrary transactional query for setup/assertion.
- Query layer exposes clearly suffixed test-only readback helpers.
- Repository/query integration uses the real DB; end-to-end behavior belongs to acceptance tests.

## Checklists

New table:

1. Migration (or pre-release init extension).
2. Central table-name config + every environment/test copy.
3. Row, schema order preserved.
4. Queries: shared fields, operations, wiring.
5. Repository: error mapping + dependency wiring.
6. Local and deployed roles/grants.
7. Real-DB integration tests.

New column:

1. Migration: pre-release init only before shipping; otherwise new version.
2. Row field at exact column position.
3. Shared query field list; update `SET` optional parameter/fragment if applicable.
4. Repository signature; caller-facing validation/domain/contract layers.
5. Explicitly pass/assert `arbitrarySample[Option[...]]` for the new update parameter; use `.orElse` for nullable columns and `.getOrElse` for non-null columns. Defaults can hide missed call sites.
6. Update strict mock expectations with the argument; never loosen matching to compile.
