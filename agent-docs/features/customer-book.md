# Customer Book

Tenant-scoped address book for billable people and companies.

## Scope

Owns:

- `customer`: the only future order target; composite PK `(organization_id, customer_id)`.
- `customer_business_contact`: people inside a business; never customers/order targets.
- `Individual`/`Business` discrimination and one-way archival.

Excludes orders and tenant membership/roles ([Organization Management](organization-management.md)). Here “organization” means the Mesazon tenant; every endpoint uses `X-Organization-ID`.

## Release constraints

The ten record operations use `/customer-book`; customer extraction is `POST /customer-book/file/ai/extract` (see [Image, CSV, and Excel extraction](#image-csv-and-excel-extraction)). Legacy verb-first routes, standalone contact mutations, separate type-specific batches, unused transport/domain models, validators, repository methods, client methods/codecs and their obsolete tests are removed. Only the mixed batch remains alongside the two singular inserts. Extraction models and shared ownerless values remain intentionally separate from record-service models.

This is a breaking API/schema release. `V2025.05.27__init.sql` defines archive fields for fresh databases only; editing an already-applied init does not upgrade that database. No upgrade/backfill migration or deployment operation is included. Drain/stop the old gateway for the coordinated cutover. Old binaries and the Boolean archive schema cannot coexist; rollout and rollback require matching schema/binary pairs. Partial-address JSONB also prevents safely rolling back to a binary that requires every address part. Verification uses disposable databases.

## Model and invariants

The current schema has `customer` holding `customer_type`, shared `name`, `emails`/`phone_numbers`/`addresses` JSONB lists, optional business-only `tax_id`, `is_archived`, and audit timestamps. `customer_business_contact` holds `(organization_id, customer_id, customer_business_contact_id)`, name, role, optional email/phone, `is_archived`, and a tenant-scoped FK to `customer`.

- One row + discriminator makes a customer exactly one type. Typed reads/updates filter `customer_type`; wrong-type lookup is not found.
- Repository views: `CustomerIndividualDetailsRow` (`fullName`) and `CustomerBusinessDetailsRow` (`businessName`, `taxID`); no `CustomerRow`. `CustomerSummaryRow(customerID, name, customerType)` is a projection.
- Contacts exist only for businesses by service convention; the FK enforces tenant, not subtype.
- Customers store email/phone lists. Each entry contains value + `isDefault`; empty is valid, non-empty requires exactly one default. Business contacts retain one optional email/phone and no address.
- Customers store an address list of `CustomerAddressEntry` (`RefinedType[AddressEntry, Pure]`, like `CustomerPhoneNumber` over `PhoneNumber`). The shared `AddressEntry(address: Address, addressType: AddressType)` pairs an `Address` with its required type (`Shipping`/`Billing`/`ShippingAndBilling`, shared with [Organization Management](organization-management.md)). All five owner-less `NonEmptyTrimmed` address-part newtypes (`addressLine1`, `addressLine2`, `city`, `postalCode`, and `country`) are optional in Smithy and the domain model. `AddressValidator` validates every supplied text value unchanged: missing/null fields become `None`, while empty, whitespace-only, untrimmed, or overlong strings produce field-specific errors containing the original value. An entry with no non-whitespace text is rejected using indexed `InvalidFieldError("address", "At least one address field must be provided", Seq.empty)`. The address-type combination is checked first; an invalid combination returns only the `addresses` error and skips every entry's field validation. For a valid combination, `validateAddressHasAtLeastOneFieldNonEmpty` uses `trimAndFilterNonEmpty` only to check for non-whitespace content; field validation receives the original values unchanged. The presence error accumulates before field errors: all-missing entries return only the indexed `address` error, while blank-only entries also report each supplied invalid field. No default rule. Allowed combinations remain empty, exactly one entry typed `ShippingAndBilling`, or exactly two entries, one `Shipping` and one `Billing` in either order; contents are not compared. The rule applies to individual/business inserts and updates, including mixed batches; the request validator wraps the validated entries in `CustomerAddressEntry`. The address object and `addressType` remain required. Existing populated JSONB documents decode into `Some` values, so stored lists are not re-checked, cleaned up, or migrated. This is an intentionally breaking single release: once a partial address is stored, the prior binary cannot safely decode that row, run alongside the new version, or be used for rollback.
- Validation accumulates all list errors. `InvalidFieldError.index` identifies the item. Batch customer errors use the outer customer index while preserving nested contact indexes.
- Customer archive state is `isArchived: Boolean` / `is_archived boolean not null`, before audit fields in both typed Rows and explicit projections. Inserts supply `false`, archive sets `true`, and non-archived predicates use `is_archived = false`; no native lifecycle enum or cast remains. The contact flag follows `updated_at` in its Row, shared projection and init schema; new contacts explicitly start non-archived. Contact archive updates only the flag and `updated_at` for matching active contacts, and repeated archive retains the first archive timestamp. See [Repository flow](flow/04-repository.md#queries).
- Customers archive. Contacts have a persisted `isArchived` flag; the storage model retains archived rows. Contact email/phone values may be repeated across active and archived contacts. Contacts are inserted, updated, or archived through atomic business PUT. Customer archive retains contacts and their archive states. No unarchive.

Named uniqueness:

| Constraint/index | Rule | 409 message |
|---|---|---|
| `uq_customer_name` | active `(organization_id, customer_type, name)`; partial on `is_archived = false` | `A customer with the given name already exists in this organization` |

Contact email/phone fields remain optional and retain their existing value validation; repeated values are accepted. Customer-name SQL state `23505` with `uq_customer_name` maps to `ConflictError.UniqueConstraintViolation`.

## Endpoints

Service: `CustomerBookService`; bearer + completed onboarding. Reads allow `Owner|Admin|User`; writes allow `Owner|Admin`. A caller with no membership row in the named organization gets `500` (`AuthorizationService.verifyOrganizationRole` fails with `InternalServerError.UnexpectedError`), not `403`; only a member with a disallowed role gets `403`. This applies to `/customer-book/file/ai/extract` too.
Smithy JSON requests are limited to 5 MiB by `HttpApp.SmithyMaxEntitySize`.

| Method | Path | Operation | Result/effect |
|---|---|---|---|
| GET | `/customer-book/individual/{customerID}` | `CustomerBookIndividualGet` | non-archived individual details |
| GET | `/customer-book/business/{customerID}` | `CustomerBookBusinessGet` | non-archived business details and active contacts |
| GET | `/customer-book/uniqueness` | `CustomerBookUniquenessGet` | read-only same-type active-name uniqueness with optional self exclusion |
| GET | `/customer-book/summary` | `CustomerBookSummaryGet` | active summaries; empty/omitted IDs fetch all, populated IDs filter |
| POST | `/customer-book/individual` | `CustomerBookIndividualPost` | one individual, returns its customer ID |
| PUT | `/customer-book/individual/{customerID}` | `CustomerBookIndividualPut` | update active individual; omitted lists retained, present lists replace |
| POST | `/customer-book/business` | `CustomerBookBusinessPost` | one business + inline contacts, returns its customer ID |
| PUT | `/customer-book/business/{customerID}` | `CustomerBookBusinessPut` | update active business and contacts atomically; omitted lists kept and nullable values clearable |
| POST | `/customer-book/batch` | `CustomerBookBatchPost` | atomic mixed batch, returns individual IDs then business IDs, each in request order |
| PUT | `/customer-book/{customerID}/archive` | `CustomerBookArchivePut` | bodyless, type-independent archive; retains customer/contact rows |

Smithy: `smithy/CustomerBookService.smithy`, `smithy/domain/CustomerBook.smithy`. Operation-level request/response wrappers retain their operation names. Nested shapes and lists for the same domain concept are shared when members, traits, validation and defaults match: business GET uses `CustomerBusinessContact` / `CustomerBusinessContacts`, and summary GET uses `CustomerSummary` / `CustomerSummaries`. POST responses use only customer IDs. Insert/update views stay separate where their contracts differ.

Error sets:

- Detail/summary reads and customer archive: `BadRequest, Unauthorized, Forbidden, InternalServerError`.
- Uniqueness read: above plus `ValidationError` for absent name/type or an invalid name.
- Other writes: above plus `ValidationError` and `Conflict`.
- Customer archive contains only pure UUIDs, cannot validation-fail, and cannot create uniqueness conflicts.
- By-ID reads must filter organization, type and non-archived state; missing/archived/wrong-type/foreign targets follow the existing `500` policy. Both typed queries implement archive exclusion. Mutations retain their lenient no-op policy.

## Flow and decisions

### Create

- Individual inserts write `customer_type = Individual`, `is_archived = false`, and `tax_id = NULL`. Business inserts write `customer_type = Business`, `is_archived = false`, and all inline contacts in one transaction.
- The mixed batch uses multi-row statements inside one `transactionOrWiden`; every parent/contact write succeeds or rolls back together. Empty batches are valid.
- The repository generates IDs and one timestamp per operation. Batch IDs stay paired with their inputs; results preserve individuals first, then businesses, and each input list's order. Singles return `CustomerID`; mixed inserts return `List[CustomerID]`, including `Nil` for empty input.
- Insert queries return `TranzactIO[Unit]` through `.update.run.void`, without SQL `RETURNING` or follow-up reads. After the transaction succeeds, the repository yields its already-generated IDs. The service maps these directly to `200` responses containing only required `customerID` or `customerIDs` (the latter reuses Smithy `CustomerIDs`); contact IDs and full values come from detail GETs. See the shared [create-response standard](../standards/smithy.md#resource-create-responses).

### Update and contact actions

Names are optional and nonclearable. Customer email/phone/address lists use `Option[List[Entry]]` without Smithy `@default([])` or `@nullable`: omitted keeps, `[]` clears, and a populated list replaces after validation. Create lists retain empty defaults. Business `taxID` and contact `role`/`email`/`phoneNumber` use nullable scalar options (`Option[Option[T]]`): omitted keeps, `null` clears, and a value replaces.

Business contact insert/update/archive lists default empty and leave unnamed contacts unchanged. `CustomerBusinessContactUpdate` has a required contact UUID, optional nonclearable name and nullable scalar fields; `CustomerBusinessContactArchive` contains only its ID. Insert/update views differ from the shared GET view because their requiredness and nullable semantics differ.

Validation accumulates errors in request order. Insert/update entry failures use singular action names and item indexes. Repeated IDs report the second and subsequent indexes in the corresponding update/archive member; update/archive overlap reports each overlapping archive index after archive duplicate errors. Duplicate or overlapping IDs fail with `400 ValidationError` before any write. Contact email/phone values need not be unique.

`updateCustomerBusiness` accepts flat optional parent fields plus `updateCustomerBusinessContactInputs`, `customerBusinessContactInputsInsert` and `customerBusinessContactIDsArchive` (empty by default). `UpdateCustomerBusinessContactInput` owns the ID and partial fields. Within one transaction, update the active business, validate referenced active contacts, merge changes, insert new contacts and archive named contacts. The parent UPDATE locks its row; contact-reference reads use `FOR UPDATE`. One timestamp covers all writes; inserted contact IDs are generated before the transaction, following Catalogue.

Missing/archived/wrong-type/foreign parents return `204` without child writes. Missing/archived/foreign update-contact references fail with the Catalogue-style `UnexpectedError`/HTTP `500` and roll back parent/contact writes. Archive-contact references in those states are no-ops. Preserve domain errors across rollback; database failures retain named constraint mapping.

### Archive and detail reads

Archive is bodyless and type-independent: its UUID comes only from the path, organization scope from the header. `archiveCustomer` returns an optional affected ID, discarded by the service with `.unit`; no request validator is needed for this pure UUID input. Archive sets the customer flag, retains contacts and their archive states, and frees the active name. Missing/already-archived archive and other mutations targeting unavailable parents return silent `204`. No unarchive exists; any future reactivation must resolve active-name conflicts.

Detail GETs stay type-specific. Clients choose the individual or business endpoint using summary `customerType`; there is no unified getter, discriminator in either detail response, or separate business-contact GET. Individual GET returns required ID/full name/email/phone/address lists. Business GET returns required ID/business name/value lists/active contacts and optional tax ID, without individual fields.

`getCustomerIndividual` and `getCustomerBusiness` are the repository read boundaries. The latter calls `getCustomerBusinessWithContactsRow`: one explicit left-join projection decodes required business details and an optional whole contact Row, then groups them into `CustomerBusinessWithContactsRow`. Join keys include organization and customer; contact `is_archived = false` belongs in `ON`, preserving a non-archived parent with zero or only archived contacts. Contacts retain IDs/full names/optional role/email/phone and are ordered by `created_at ASC, customer_business_contact_id ASC`.

Both typed queries filter organization, type and non-archived parent state in `WHERE`. Missing/archived/wrong-type/foreign targets return `None`, mapped to the existing exact missing-row `UnexpectedError`/HTTP `500`; an archived business returns neither parent nor contacts. All stored rows remain unchanged. Service mappings use inline Chimney transformations; database read failures map directly to `RepositoryError`.

### Summary and uniqueness

`getCustomerSummaries(organizationID, customerIDs: List[CustomerID])` runs one tenant-scoped active query. An empty/omitted list fetches all active customers; a populated list adds parameterized `IN`. Unknown/archived/foreign IDs are skipped, repeats return each customer once, and both modes sort by `LOWER(name), customer_id`. `NonEmptyList.fromList` gates only the SQL predicate. The service forwards the ordinary list unchanged and preserves repository order under required JSON member `customers`; `CustomerSummary` carries ID, name and type. Repeated UUID query parameters preserve submitted order/repetitions; `Nil` omits the parameter. No payload model or validator is needed.

`CustomerBookUniquenessGetRequest` requires a trimmed 1–255-character `CustomerName` and `CustomerType`, with optional self-excluding `customerID`. Smithy query members are optional so missing name/type produce ordered validation errors (name, then type); an unknown typed enum or malformed UUID fails transport decoding with `400 BadRequest`. Supplied invalid names retain their submitted values.

`isUniqueCustomerName(organizationID, customerName, customerType, customerIDOpt)` uses exact case-sensitive equality within the organization/type, filters non-archived customers and optionally excludes only that ID. The required `isNameUnique` result preserves true and false. This check does not write or reserve names; write-time uniqueness remains authoritative. All organization roles may read, so no disallowed-role case is constructible. Pure SELECT failures map directly to `RepositoryError`. Catalogue's missing self-exclusion remains [deferred to its next PR](catalogue.md#known-issues-edge-cases-and-larger-follow-ups).

### Layer boundaries

Repository inputs never use API request types. `CustomerBookRepository` owns reusable nested/batch inputs; singular inserts reuse them, while single-only updates remain flat. Service mapping follows [Chimney](../standards/chimney.md). JSONB Rows and named codecs use `List[CustomerEmailEntryInput]` and `List[CustomerPhoneNumberEntryInput]`; addresses use `List[CustomerAddressEntry]` directly. `AddressType` is stored as its case-name string. Queries import repository companion inputs and `io.github.iltotore.iron.jsoniter.given`.

Org isolation comes from composite keys/FKs. Future order history must retain customer rows and snapshot buyer fields with `on delete restrict`. Typed `GatewayClient` request parameters use plain request names without `Smithy`; handler/validator/test domain-versus-transport naming follows the shared standards. Simple assertion counts and positional indexes stay inline; persistence readbacks target the scenario rather than adding blanket empty-table checks.

### Contract and upload design

- **Wire format of empty lists.** The response codec is the default `JsonCodecMaker.make`, as for Catalogue, so an empty `inferredFields`, `missingFields`, `duplicateFields`, `extractionNotes` or address list is omitted from the JSON rather than sent as `[]`; clients treat an absent list as empty. The acceptance spec compares decoded models, so it proves the decoded value, not the omission.
- **Acceptance fake.** `CustomerBookFileApiSpec` uses its own WireMock mappings in `backend/wiremock/mappings/` (`ai-client-chat-completions-customer-book-file-*.json`): the extraction mappings match the request body on `Return exactly one CustomerBookFileAIExtract` and `json_schema`, like the Catalogue mapping (the multi-group one also on `AI_CLIENT_SPEC_BATCH_NOTES`), and the compaction mapping matches the compaction prompt and `json_schema`. Changing them requires rebuilding the WireMock image (`wiremock/Docker/publishLocal`). The `contact-book-spreadsheet-it-3.xls` fixture is a copy of the Catalogue one; the stubs ignore file content. Needs Docker; not runnable without it.

- **Transport stays the raw `streamBinaryBody`** — not multipart and not Smithy4s. sttp-tapir 1.13.31 has no streaming multipart part type, while http4s multipart decoding and this project's Smithy4s 0.19.12 http4s interpreter buffer the body in JVM heap before application code can apply `FileScanner`'s disk-backed cap. The raw Tapir stream preserves the bounded-write/full-drain behavior required by [Streaming uploads](../project/streaming-uploads.md).
- `X-File-Name` is validated, used as a Tika detection hint, compared with the scanned file, and never stored. A missing or malformed header decodes to the generic `400 BAD_REQUEST_ERROR`; mismatch details use the same public error and remain visible only in server logs. Client-supplied content type and size are not part of the contract: the scanner independently determines the media type and actual byte count.
- `X-Processing-Message` is an optional raw `Option[String]` header, exactly as Catalogue: the handler trims it, blank becomes absent, and `CustomerBookFileProcessingMessage` (`NonEmptyTrimmedMessage`, up to 2,000 characters) validates the rest; invalid guidance maps to the existing `400 BAD_REQUEST_ERROR` before any scan or AI call. The message is sent as a separate lower-priority user message after the source content, applied to every batch, never stored or returned. Guidance cannot override domain constraints, computed flags, or counts.
- `CustomerBookFileExtractFileName` (`String` with `NonEmptyTrimmed`) is required, never an `Option`. `FileScanner` stays feature-neutral and receives the plain string.
- `FileScanner` exposes only `scan(fileByteStream, fileNameDeclared, supportedMediaTypes, fileBytesMax)`. It performs the bounded disk write, uses the declared filename as a Tika hint, detects the media type, and validates it against the type selected by the filename extension (case-insensitive; `jpg` and `jpeg` both map to JPEG). A malformed declaration, unsupported detected content, or mismatch fails with `ServiceError.BadRequestError`; an unreadable stream and actual content over the configured cap keep `ServiceError.InternalServerError`, and the network stream is still fully drained and counted.
- File-service naming follows the [Tapir naming rules](../standards/tapir.md#naming): path segments declared separately, endpoint `customerBookFileAiExtractPostEndpoint`, service method `aiExtract`, response `CustomerBookFileAiExtractPostResponse`.
- Do not add an over-20-MB HTTP acceptance case: the known `EntityLimiter`/Ember hang remains open; `FileScannerSpec` proves the byte cap directly.

**Risk and rollback (MEDIUM):** this repeats a pattern already shipped for Catalogue, with no schema or stored-data change and no new dependency. The public route and response shape are both breaking, with no compatibility overlap, so clients and gateway roll forward or back together; rollback restores the previous release. The open oversized-body hang still excludes an over-limit HTTP test.

### Models and ownership

The AI result and the public response are separate types (see the [AI extraction standard](../standards/ai-extraction.md#models-and-structured-output)). `CustomerBookFileAIExtract` and its nested `*AIExtract` types live in `domain/gateway/CustomerBook.scala`, register in `json/ai.scala` as a strict OpenAI schema with a `JsonCodecMaker` codec, and are never returned to clients. Public types register in `json/tapir.scala`. Field naming follows the [AI extraction standard](../standards/ai-extraction.md#field-naming-and-attention): `<Thing>AIExtract` for the AI result, `<Thing>Candidate` for the public preview, `<field>Inferred` for descriptive flags. There is no duplicate flag: the service computes duplicates per candidate (see Duplicates below).

AI model (what the model returns). Every value uses its strict domain type. The schema sent to OpenAI carries only the email pattern and 255-character limit and the `AddressType` enum; the `NonEmptyTrimmed` rule (trimmed, 1-255 characters) on names, phone parts, tax ID, role and address text is enforced only when the answer is decoded, so the prompts must state it. A value breaking its constraint fails the whole read (epic requirement 2, see the accepted trade-off below). Absence is `None`, and is never mirrored by a `missing…` flag:

- `CustomerBookFileAIExtract(entriesIdentified: Long, entriesProcessed: Long, individualCandidates, businessCandidates, emptyEntryRowIndexes: List[Long], unidentifiedEntryRowIndexes: List[Long], extractionNotes: List[String])`. Counts and row findings are AI-reported; semantic validation of them is out of scope, as in Catalogue.
- `CustomerIndividualAIExtract(fullName: Option[CustomerFullName], emails: List[CustomerEmail], phoneNumbers: List[CustomerPhoneNumberAIExtract], addresses: List[CustomerAddressEntryAIExtract], fullNameInferred: Boolean, extractionNotes: List[String])`.
- `CustomerBusinessAIExtract(businessName: Option[CustomerBusinessName], emails: List[CustomerEmail], taxID: Option[CustomerTaxID], phoneNumbers: List[CustomerPhoneNumberAIExtract], addresses: List[CustomerAddressEntryAIExtract], customerBusinessContacts: List[CustomerBusinessContactAIExtract], businessNameInferred: Boolean, extractionNotes: List[String])`.
- `CustomerBusinessContactAIExtract(fullName: Option[CustomerFullName], role: Option[CustomerBusinessContactRole], email: Option[CustomerEmail], phoneNumber: Option[CustomerPhoneNumberAIExtract], fullNameInferred: Boolean, extractionNotes: List[String])`.
- `CustomerPhoneNumberAIExtract(phoneNationalNumber: PhoneNationalNumber, phoneCountryCode: Option[PhoneCountryCode], phoneCountryCodeInferred: Boolean)`. The number is required: a phone whose number cannot be read is not returned and the model notes it.
- `CustomerAddressEntryAIExtract(address: CustomerAddressAIExtract, addressType: AddressType)` with `CustomerAddressAIExtract(addressLine1: Option[AddressLine1], addressLine2: Option[AddressLine2], city: Option[City], postalCode: Option[PostalCode], country: Option[Country], extractionNotes: List[String])`.
- The AI model carries no `isDefault`: the service sets defaults. It carries no attention flag and no `missing…` flag.

  |---|---|
  | `/fullName` (person), `/businessName` (business) | `missingFields` when `None`; `inferredFields` when `fullNameInferred`/`businessNameInferred`; `duplicateFields` when the name is a duplicate |
  | `/phoneNumbers/{i}/phoneNumber/phoneCountryCode` (i = position in the candidate's phone list) | `missingFields` when the AI returned no country code; `inferredFields` when `phoneCountryCodeInferred` is true |
  | `/customerBusinessContacts/{i}/fullName` (i = position in the AI's contact list) | `missingFields` when the contact's name is `None`; `inferredFields` when `fullNameInferred` |
  | `/customerBusinessContacts/{i}/phoneNumber/phoneCountryCode` (i = position in the AI's contact list) | `missingFields` when the contact's phone has no country code; `inferredFields` when `phoneCountryCodeInferred` is true |

  Each path is built from the response's own property names by one small helper that escapes `~` and `/`, as the [AI extraction standard](../standards/ai-extraction.md#structured-field-reporting) requires, and a functional test resolves every reported path against the serialized candidate JSON. The lists are never de-duplicated and keep AI order. A contact's phone is a single optional entry, so its index is the contact's position. The same pointer rule works at any nesting depth, so a new nested path needs no new client logic.
- Loose preview types, because `PhoneNumber` also carries the derived `phoneRegion` and `phoneNumberE164`, which a preview must not invent: `CustomerPhoneNumberCandidate(phoneNationalNumber: PhoneNationalNumber, phoneCountryCode: Option[PhoneCountryCode])` (a missing code is `None`, reported in `missingFields`; the candidate cannot be added until the user supplies it), `CustomerPhoneNumberEntryCandidate(phoneNumber: CustomerPhoneNumberCandidate, isDefault: Boolean)`, and `CustomerBusinessContactCandidate(fullName: Option[CustomerFullName], role: Option[CustomerBusinessContactRole], email: Option[CustomerEmail], phoneNumber: Option[CustomerPhoneNumberCandidate])`. Emails reuse `CustomerEmailEntry` and addresses reuse `CustomerAddressEntry`.
- The preview runs no add validators (phone realness is checked only when the candidate is added; the address combination is already guaranteed by `computeAddressEntries`), so a candidate is not the validated insert request. Emails, the candidate's and a contact's, pass only the `CustomerEmail` Iron predicate on decode (`EmailPredicate`: `^[^@\s]+@[^@\s]+\.[^@\s]+$`, max 255); `EmailValidator` (trim, lower-case, JMail RFC 5322 check) runs only on the add request, so a preview email keeps the AI's casing and may still be rejected when added.

### `CustomerBookFileService.aiExtract`

`aiExtract(organizationID, customerBookFileExtractFileName, customerBookFileProcessingMessageOpt, customerBookFileExtractByteStream)` runs inside one `ZIO.scoped` block:

1. `FileScanner.scan` spools the stream to a scoped temp file, validates it against `SupportedMediaType.extractData`, and enforces `customerBookFileServiceConfig.extractCustomersFileBytesMax`.
2. Images pass the `FileScannedPath` and detected media type to `AIClientDataExtraction.extractFromImage[CustomerBookFileAIExtract]` with the image instructions and the optional processing message.
3. Excel files pass the path to `SpreadsheetTool.convertExcelToCsv` and CSV files to `SpreadsheetTool.convertToCsv`; the resulting record stream goes once to `extractFromCsv[CustomerBookFileAIExtract]` with the file instructions and the optional message. The client owns batching and returns one decoded result per group as a `NonEmptyChunk`, in group order. Any group failure fails the whole request.
4. **Merge** (spreadsheets only; an image has a single AI result and is neither merged nor compacted): the pure `mergeCustomerBookFileAIExtracts` sums `entriesIdentified` and `entriesProcessed` and concatenates both candidate lists, `emptyEntryRowIndexes`, `unidentifiedEntryRowIndexes` and `extractionNotes` in group order, returning a plain `CustomerBookFileAIExtract`. It finds no duplicates and never combines or de-duplicates notes. For two or more groups, `aiExtract` then compacts the merged top-level notes (see [Notes compaction](#notes-compaction)); if that is skipped or fails, the raw concatenation is what the response carries, so a note can repeat.
5. The service reports what it can derive from the AI's values as structured `FieldInfo` lists and maps with Chimney. The AI handles everything else (what to return, what to leave out, and the notes explaining it):
   - **Duplicates** (every source, inside the field computation): the AI models carry no duplicate flag. `aiExtract` counts the defined names of the single or merged extract once per kind (`computeCustomerIndividualFullNameCounts`, `computeCustomerBusinessNameCounts`, each a `Map[name, Int]`), and passes the counts to `computeCustomerIndividualFields` / `computeCustomerBusinessFields`, which compute `duplicateFields` the same way they compute `missingFields` and `inferredFields`. A named candidate is a duplicate when its name occurs more than once among same-kind names, exact and case-sensitive (the comparison of `uq_customer_name` and `isUniqueCustomerName`, whose names are already trimmed). Nameless candidates are never duplicates; a person and a business with the same name are not duplicates; never compared with stored customers.
   - **Field reporting** (pure `compute...` functions over the AI values only): `inferredFields`, `missingFields` and `duplicateFields` as defined by the `FieldInfo` vocabulary above, for the candidate's name, each of its phones, and (businesses) each contact's name and phone. Inferred values, left-out details, partial addresses, left-out addresses and set address types are never `missingFields`. No add validator runs: phone realness is checked only when the candidate is added; the address combination is guaranteed by `computeAddressEntries`.
   - **`needsAttention`**: `duplicateFields.nonEmpty || missingFields.nonEmpty`. So a missing or duplicate name, a contact with no name, or a phone without a country code (the candidate's own or a contact's) marks the candidate; `inferredFields` never does.
   - **`extractionNotes`**: in this order: the candidate's AI notes, the AI notes of every address in list order (kept, all-empty dropped and left out by the cap alike), one service note per address left out by the two-address cap (`Address left out: <value>`, below), then (businesses) each contact's AI notes in AI-list order, unprefixed. The service writes no other fixed notes (none when it sets address types); the position of a contact or phone is told by the position inside `FieldInfo.path`.
   - **Addresses** (`computeAddressEntries`, pure, per candidate, over the AI's addresses in the AI's order): first the all-empty addresses are dropped (their AI notes stay). Of the rest, only the first two are kept; each further one gets the note `Address left out: <value>`, where `<value>` is its first non-empty text field in the order line 1, line 2, city, postal code, country (computeAddressLeftOutNote), written after all the address AI notes, in the order of the left-out addresses. The AI notes of a left-out address stay. Then the types: one address is always `ShippingAndBilling`; two stay as the AI typed them when they are one `Shipping` and one `Billing` in either order, otherwise the first is `Shipping` and the second `Billing`. No count limit and no single-address rule are in the prompt, and no note is written when a type is set or changed. The result is always none, one `ShippingAndBilling`, or one `Shipping` plus one `Billing` (functional rule 6 of the epic's [Requirements across the epic](../../pages/epics/05-customer-book.md#requirements-across-the-epic)); none of it marks a candidate. Candidate-level notes are never de-duplicated or compacted; only the top-level notes are, and only for a multi-group spreadsheet.
   - **Mapping** (Chimney, inline, no private mapping helpers): emails become `CustomerEmailEntry` with the first `isDefault = true`; every phone is mapped to `CustomerPhoneNumberCandidate` (its country code stays `None` when the AI returned none), the first phone is the default; addresses become `CustomerAddressEntry` from the AI address (the address's `extractionNotes` are not part of the entry) after the filtering, cap and typing above; contacts are mapped with their optional name. The service does not otherwise filter or drop candidates or contacts: what the AI returns is what is mapped.
   - **`infoNotes`**: always `Processed <entriesProcessed> of <entriesIdentified> entries` (the AI's counts of original entries, so 346 processed entries and one empty row in a 347-row file read `Processed 346 of 347 entries`), then `Candidates created <n>` only when the candidates the service counts (individuals plus businesses) differ from `entriesProcessed`, then `Empty rows (<n>) at [<rows>]` and `Unidentified rows (<n>) at [<rows>]` (for example `Empty rows (1) at [6]`, the same shape for any count) only when non-empty, in that order, with the real row numbers (for an image, the AI's best-effort positions of the visible entry lines, numbered from 1; an image has no empty rows). Titles, totals, headings and follow-on contact rows count nowhere. Top-level `extractionNotes` are the AI's general notes, including the nothing-found sentence; an entry that could not be returned may also be mentioned there.
6. No `ImageProcessing.normalize` step, no `S3Client` call and no repository write for any source: nothing is persisted and the response is not remembered.

The shared AI extraction client selects a configurable model per operation for both catalogue and customer extraction: `ai-client-data-extraction.image-model` defaults to `gpt-6.1-sol` and `csv-model` (including converted spreadsheets) to `gpt-6.1-terra`, overridden by `AI_CLIENT_DATA_EXTRACTION_IMAGE_MODEL` and `AI_CLIENT_DATA_EXTRACTION_CSV_MODEL`. Each operation also has a reasoning-effort setting (`image-reasoning-effort` defaulting to `medium`, `csv-reasoning-effort` to `low`, overridden by `AI_CLIENT_DATA_EXTRACTION_IMAGE_REASONING_EFFORT` and `AI_CLIENT_DATA_EXTRACTION_CSV_REASONING_EFFORT`). The client forwards each configured effort to its operation; use a value supported by the selected model. Protocol tests and WireMock request matchers do not pin model names. Live quality and latency after a model override require manual verification.

`AIInstructions` owns two customer prompts, `private[gateway] lazy val extractCustomersFromImageInstructions` and `extractCustomersFromFileInstructions`, beside the Catalogue prompts. They describe the exact AI schema above and tell the model that uploaded content is source data, not instruction authority. The processing message is not part of them. Rules both prompts give, none of which the service re-checks unless stated:

- **Row numbers (file prompt).** Every row, including the header, carries a leading `Row Number` column that is that row's real file position; it must be used, never the model's own count, whenever a row is named. A row whose columns after Row Number are all empty is blank: never an entry, its number goes in `emptyEntryRowIndexes`. A non-blank row with no readable name and no qualifying email, but with at least one usable detail (an email, a phone with a readable national number, since its country code is optional in the schema, an address with at least one non-empty field, a tax ID, or a contact), is returned best-effort as a candidate with `fullName`/`businessName` `null` and is not unidentified. A non-blank row from which no name and no usable detail could be read is not a candidate and its number goes in `unidentifiedEntryRowIndexes`. The image prompt returns `emptyEntryRowIndexes` empty and reports `unidentifiedEntryRowIndexes` as the best-effort positions (1-based, top to bottom) of visible entries it saw but could not process.
- **Processing message is a general instruction.** The user's processing message (a separate user message) may instruct anything about how the source is extracted: splitting a row into several customers, adding values to an entry, completing a missing name part from the email (with `fullNameInferred = true` and a short note), or changing how optional details are read. It takes priority over the prompts' default reading rules (inference, never-invent-a-name, unreadable-detail handling, which entries are returned). Three limits stay fixed: the output must fit the response format and value rules (an unmeetable request is applied as far as possible and noted); no invented facts (it may say how to read, split, combine or derive values from what the source shows); the system computes counts, duplicates, missing fields and attention from what the AI returns, so after a split `entriesIdentified` is still `entriesProcessed` plus the empty plus the unidentified entries, and the message cannot hide missing or unclear data. A detail the message asks to drop (for example "omit phone numbers" gives `phoneNumbers: []`) is absent, not missing, and an entry it asks to skip counts nowhere. **Known gap:** the service derives `missingFields` from the returned nulls, so a phone kept without its country code because the message asked to drop only the code is still reported missing at `/phoneNumbers/{i}/phoneNumber/phoneCountryCode` and sets attention; the same holds for a name or contact name dropped on request (`/fullName`, `/businessName`, `/customerBusinessContacts/{i}/fullName` from `None`). The epic intends these to be absent, not missing ([epic gap 7](../../pages/epics/05-customer-book.md#7-a-detail-dropped-on-request-is-still-reported-missing)), and the AI has no field to tell the service. Reason: the generic "never invent a name" rule previously made the model ignore such messages. Unverified until a golden run with a processing message.
- **Name inferred from email.** When no part of an entry's name is readable but it has an email that plausibly encodes a person's name, the model infers the name from it, sets `fullNameInferred = true`, returns an ordinary candidate and adds a note such as `Name taken from the email address`. Lenient on shape (`john.smith@…`, `john@…`, `jsmith@…` read as "J Smith"); never for role or meaningless mailboxes (`info@`, `sales@`, `support@`, `noreply@`, `admin@`, `contact@`, `xk29fj3@…`); applies to an individual's name and a business contact's name. A business's own name may instead be inferred from the domain of one of the business's own company emails (`orders@acme-tools.com` reads as "Acme Tools"; sets `businessNameInferred = true`, adds a note), never from a free-mail domain (`gmail`, `outlook`, `yahoo`, `hotmail`, `icloud` and the like), a meaningless domain, or a contact's email; a partly readable name is used as read and not flagged. An inferred-name entry counts as a processed candidate and is not unidentified, and does **not** set `needsAttention`. An entry with neither a readable name nor a qualifying email has `null` name.
- **Unreadable parts.** A detail the model cannot read is never invented. An unreadable email, or a phone whose number cannot be read, is omitted and the model writes its own short note (for example `An email address could not be read`), keeping the rest of the entry; a phone with a readable number but no country code that cannot be worked out from clear context is returned with `phoneCountryCode` `null` and the model notes it (the service keeps the phone with no country code and reports it in `missingFields`, which sets `needsAttention`); a contact with no readable name has `fullName` `null` and is returned when it has a readable role, email or phone (with none of those it is not returned). It returns nothing for details the source does not show (empty cells and columns are absent, not unreadable). Details omitted at the processing message's request are absent, never unreadable.
- **Phones.** Best-effort national number plus country code, e.g. `{"phoneNationalNumber":"4155550123","phoneCountryCode":"+1","phoneCountryCodeInferred":false}`. A missing country code may be inferred from context (the entry's own address, one country used across the source, or the processing message); the model then sets `phoneCountryCodeInferred = true` and adds a note on the phone's owner giving the basis. When the clues conflict (for example an 8-digit Cypriot-format number in a Cypriot file beside a Greek city) it still returns its most plausible code, preferring the country whose number length and format fit together with the country used across the source or the processing message; the address is weaker evidence and does not veto the guess, and the note says it is a guess that does not match the address. Only when no country is even plausible is the value `null` with `phoneCountryCodeInferred = false` and a note giving the reason. No libphonenumber check runs at extraction: the code is the model's judgment, and phone realness is still checked only when the customer is added. When the source clearly marks one email or phone as the main one, it is listed first (the service marks the first entry as default); otherwise source order.
- **Addresses.** `{"address": {addressLine1?, addressLine2?, city?, postalCode?, country?, extractionNotes}, "addressType"}`, optional properties nullable under the existing required-property adapter, `addressType` a strict `Shipping`/`Billing`/`ShippingAndBilling` enum. Missing, null, empty and whitespace-only text is empty; keep an address when at least one text field has non-whitespace content, request trimmed populated values and a note for missing or unclear fields. Repeated addresses within a candidate are merged first (all five fields match after trimming, ignoring type); never across candidates. The model has no count limit, no single-address rule and no assumed-type note: it only identifies, as best it can from the source, which address is billing and which is shipping and marks each `addressType` accordingly. The service then caps the list to two, sets the final types and writes a note per address left out (see `computeAddressEntries` above).
- **Duplicates.** The prompts give no duplicate rule (they only say the server computes duplicates) and the models carry no duplicate flag. The service marks a name that is exactly equal (capital letters count) to another candidate's name of the same kind across the whole upload; a nameless candidate is never a duplicate, and the AI does not decide attention.
- **Note scopes.** Because the service concatenates notes without de-duplication, the prompts give each note one scope: top-level `extractionNotes` hold only whole-image or whole-batch comments (tentative label interpretation, skipped first row, left-out lines or rows, ignored columns, a shared assumption such as one country code used throughout); a candidate's notes hold only the candidate itself and its addresses as a group (an empty address left out); an address's notes hold only that address; a contact's notes hold only that contact. The service already adds every address and contact note to the candidate's list, so the model must not repeat them there, must write each observation once at the narrowest scope, and must not restate counts, row numbers or the missing, inferred and duplicate lists. Each spreadsheet batch is a separate model call, so batch-wide top-level notes (interpretation, skip note, ignored columns, shared assumptions, the empty-result note) can repeat once per batch; the prompt cannot prevent it, and `aiExtract` combines them afterwards, see [Notes compaction](#notes-compaction).
- **Notes.** Candidate, address, contact and general `extractionNotes` are plain-string arrays, one point per entry, no bullets, each at most ten words (a hard prompt rule, stated once in every prompt, Catalogue's included), in plain everyday words a customer would understand (never technical words such as "infer", "context", "schema" or "format codes"), never with a semicolon: a longer observation is split into several notes or shortened, and a long list of names is summarised, not enumerated (`Eight marketing columns were not used`). Routine unchanged values need no comment. The service writes notes only for the addresses it leaves out (`Address left out: …`): duplicate, missing and inferred facts reach the client through `duplicateFields`, `missingFields` and `inferredFields`. The model explains every left-out, unreadable or inferred detail, every phone kept without a country code (the reason, for example `Phone country code is not shown`) and every partial address in its own words, and must not write a note that only says a name is missing or duplicated or that a contact has no name. An entry that could not be returned (an image, or a spreadsheet row that is neither blank nor a candidate) is described in the top-level notes.
- **Counts and empty results.** The model reports `entriesProcessed` and `entriesIdentified`, defined in the prompts. `entriesProcessed` is how many original entries (file rows or visible image entries) were read and processed into at least one candidate: an entry split into several candidates counts once, and entries the processing message asks to skip count nowhere. `entriesIdentified` is the total: `entriesProcessed` plus the number of `emptyEntryRowIndexes` plus the number of `unidentifiedEntryRowIndexes`. The multi-group merge sums both; the service never validates them. The candidate lists are the people actually created and can outnumber `entriesProcessed`, so `infoNotes` read `Processed <entriesProcessed> of <entriesIdentified> entries` and add `Candidates created <n>` (individuals plus businesses, counted by the service) only when `n` differs from `entriesProcessed`. Each customer counts once, a contact adds no entry, and repeated header, title or total rows are neither blank nor unidentified and count nowhere. When nothing recognizable is found the model returns zero counts and empty lists, a normal `200`; the general note is `AI could not detect relevant customer data in this image.` or `... in this file.`. The prompts forbid inventing customers from unrelated content.
- **Schema constraints stated explicitly.** Because a value breaking a strict type fails the whole read, the prompts spell out every constraint instead of relying on the schema, which does not carry `NonEmptyTrimmed`: every name, phone part, tax ID, role and address text value is non-empty, trimmed and at most 255 characters; an absent optional value is `null` and never `""` or whitespace; `phoneNationalNumber` cannot be `null`, so a phone whose number cannot be read is omitted and noted; emails match `local@domain.tld` with no whitespace and at most 255 characters (the schema also enforces this; an email that cannot be read that way is omitted and noted); and `addressType` is one of `Shipping`, `Billing`, `ShippingAndBilling`.
- **Prompt structure and process.** Both prompts follow the [prompt structure](../standards/ai-extraction.md#default-instructions-and-user-guidance): JSON shape, shape rules, (file) the Row Number paragraph, the numbered internal process (transcribe or take the supplied rows as the transcription; filter out non-customers; map labels to customer fields in any language; read each record through the mapping; supported values before user preferences; check against the source; recount), `Keep this process internal`, then the core rules. Product rules the process fixes: a name-only line or row is a customer unless it is clearly a section heading, and when unsure it is kept with a note; the document owner's letterhead, titles, dates, totals and footers are not entries (not counted, in neither row list; each is quoted in a top-level note); separate first and last name columns are joined; a cell with several emails or phones is split; the individual-or-business decision rests on evidence (company name, legal suffix, tax ID, listed contacts) and names are kept as written; a contact joins a business only from the business's own entry or row, a clear contact label or grouping, or (file) a following row with no name of its own that only adds contact details, with a note when the link is uncertain; a country code written with the number or in its own dialling-code column is read, not inferred.
- **Ignored columns and a first row that looks like data.** A column or detail with no field in the schema (balance, comment, birthday) is left out of the candidates and noted once at top level (one note per column label, not per row or candidate; Row Number and all-empty columns are skipped). A file's first row that looks like data is used only to understand the columns (as in Catalogue): it is not extracted or counted, and one top-level note says the first row looked like data and was skipped. **Known limitation:** `AIClientDataExtraction.extractFromCsv` always takes the first record as the header and repeats it, labelled `Row Number`, at the top of every batch, so in a header-less file that customer is never extracted and the skip note repeats once per batch of up to 100 rows. Fixing it needs the client to detect a header-less file (a separate slice). Reading the row as a customer was rejected because the header is repeated in every batch, which would extract it once per batch and mark the copies as duplicates.
- **Guidance.** See "Processing message is a general instruction" above: it may reshape the extraction (omit phone numbers, split a row, complete a name) within the three fixed limits.

These stay prompt rules; live-model adherence is not guaranteed and manual observations are recorded separately from deterministic tests.


### Media types

`SupportedMediaType` represents every media family with non-empty extension and MIME sets. `CSV` accepts extension `csv` and both `text/csv` and `text/plain` (Tika's common fallback detection for a real CSV file, since CSV has no binary signature); `JPEG` accepts both `jpg` and `jpeg`. `XLS` and `XLSX` retain their distinct Excel MIME types and extensions. `SupportedMediaType.extractData` is the single image-plus-spreadsheet list used by customer extraction. The narrower `images`, `spreadsheets`, `excel`, and `csv` lists drive `CustomerBookFileService`'s own dispatch among `AIClientDataExtraction.extractFromImage`, `SpreadsheetTool.convertExcelToCsv`, and `SpreadsheetTool.convertToCsv`.

#### `FileScanner` content-sniffing and filename agreement

Plain magic-byte detection cannot tell apart same-container formats: every OOXML type (`.xlsx`, `.docx`, `.pptx`) is a ZIP archive, and every legacy MS Office type (`.xls`, `.doc`, `.ppt`) is an OLE2 compound file. `scan` therefore selects the declared supported type from `X-File-Name`, writes the body to a scoped temp path, and calls Tika with that filename as its detection hint. The detected MIME must belong to the declared type's non-empty MIME set.

Extension selection happens before the body is consumed, so unsupported declarations fail fast. Size enforcement happens while the body is consumed, and media agreement is checked after the temp file is complete. The filename comparison is case-insensitive and only the final extension is used.

**Accepted trade-off:** Tika can classify a generic ZIP container as the declared OOXML subtype when given an `.xlsx` hint. `SpreadsheetTool.convertExcelToCsv` remains the structural backstop: Apache POI rejects a plain ZIP that is not a genuine workbook. The equivalent legacy-container ambiguity is also resolved by POI's workbook parse.

### `SpreadsheetTool`

`utils/SpreadsheetTool.scala` is the sole spreadsheet conversion contract, wired into `Main.scala` (`SpreadsheetTool.live`) and called directly by `CustomerBookFileService.aiExtract`. It replaced `SpreadsheetToolOld` (2026-09-21 deletion; `SpreadsheetToolOld` itself had merged what were two separate implementations, `ExcelToCsvConverter` and `CsvValidator`, both deleted earlier when that merge landed, and returned a validated `CsvValidatedPath` rather than a stream — that newtype is deleted too, along with `SpreadsheetToolOld`'s own unit spec `SpreadsheetToolOldSpec`; `SpreadsheetToolSpec` is the only remaining unit spec for this concern).

```
def convertExcelToCsv(
    excelFileScannedPath: FileScannedPath
): ZStream[Scope, ServiceError, CSVRecord]

def convertToCsv(
    csvFileScannedPath: FileScannedPath
): ZStream[Scope, ServiceError, CSVRecord]
```

Neither method takes `supportedMediaType`: Apache POI's `WorkbookFactory.create` already detects XLS vs XLSX from the file itself, and CSV needs no such dispatch at all. Each method returns the parsed CSV content as a lazy stream of records rather than a validated path: the consumer (`AIClientDataExtraction.extractFromCsv`) processes records in fixed-size batches (`aiClientConfig.csvBatchMaxDataRows`), so it never needs the whole parsed CSV in memory at once — it can pull one batch, send it, then pull the next, bounding memory to one batch's worth of records regardless of file size.

- `convertExcelToCsv` (Excel: `XLS`/`XLSX`) writes a scoped temp CSV file first, via Apache POI (`WorkbookFactory.create`, first-sheet-only via `getSheetAt(0)` — other sheets are never opened, per the epic's first-sheet-only rule) and Commons CSV's `CSVPrinter` writing straight to disk with no in-memory buffering, then streams records lazily from that written file through the same private stream-producing helper `convertToCsv` uses.
- `convertToCsv` (CSV, accepting `text/csv` and `text/plain`) streams records lazily from the given CSV path directly, with no in-memory buffering.

Records stream one at a time from Apache Commons CSV's own lazy `CSVParser#iterator()` — never `.getRecords()`, which would eagerly materialize the entire parsed CSV into a `List` regardless of source size. `SpreadsheetTool` does not filter blank rows itself; every row it emits, blank or not, reaches its caller (`AIClientDataExtraction.extractFromCsv`) unchanged. The underlying reader/parser is acquired as a scoped resource and closed when the stream completes, fails, or is interrupted, matching this codebase's convention of surfacing `Scope` explicitly in the environment type for resource-bearing operations (as `FileScanner` also does).

In both methods, parsing itself is the structural "genuinely readable as CSV" validation gate (the epic's rule that a file must be genuinely readable, not merely named or labelled, as CSV or Excel) — there is no separate validation step before parsing, and a mid-stream parse failure surfaces as the same `ServiceError.InternalServerError.UnexpectedError` as an upfront one. A Tika MIME match alone is not enough, since an arbitrary text file can be mislabelled `text/csv` or `text/plain`; a file that fails this parse is rejected the same way an unsupported file type is.

`AIClientDataExtraction` is the sole AI client for image/CSV/Excel extraction, shared with Catalogue (`it/AIClientDataExtractionSpec.scala` is its integration spec). It has two generic methods matching each source's real shape; no `supportedMediaType`-keyed dispatch lives inside it:

### Notes compaction

`AIClientDataExtraction.noteCompaction` combines Customer Book's top-level notes only, so a multi-group spreadsheet does not return the same general note once per group. It comes with `NoteCompactionOutput` and its `json/ai.scala` registrations, the `note-compaction-*` config keys (and `AI_CLIENT_DATA_EXTRACTION_NOTE_COMPACTION_*` variables) and the four `ai-client-chat-completions-note-compaction-*.json` WireMock stubs. The product rule is [epic step 8](../../pages/epics/05-customer-book.md#8-user-extracts-customers-from-an-image-or-file), requirement 22.

- **Contract.** `noteCompaction(notes: List[String], instructions: String): IO[ServiceError, NoteCompactionOutput]` with `NoteCompactionOutput(notes: List[String])` in `domain/gateway/AIClient.scala`. It is generic in the client and knows nothing about Customer Book; the prompt lives in `AIInstructions` (`compactCustomerBookFileNotesInstructions`). The call does not send the processing message.
- **When it runs.** Only in `aiExtract`'s spreadsheet branch, after the merge, when the `NonEmptyChunk` has two or more results **and** the merged top-level `extractionNotes` is non-empty. An image, a one-group file or a notes-free result makes no call. Candidate-level notes and `infoNotes` are never sent.
- **Accepting the result.** The output replaces the merged notes only if it is non-empty and has no more notes than were sent. Otherwise, and on any failure of the call (a `ServiceError` or a defect), the raw concatenation is kept, the failure is logged at warning level, and the request still succeeds. The response shape does not change and nothing tells the caller.
- **Prompt rules** (epic requirement 22): notes saying the same thing become one; only notes that say the same thing become one note in one clear wording; notes that differ even slightly in meaning or detail (rows, columns, counts) are all kept exactly as supplied; nothing else is rewritten, shortened or added; order follows each point's first appearance; plain strings, one point each, no bullet prefix.
- **Config.** `ai-client-data-extraction.note-compaction-model` (default `gpt-6-luna`), `note-compaction-reasoning-effort` (`low`) and `note-compaction-request-timeout` (`30 seconds`), each with an `AI_CLIENT_DATA_EXTRACTION_NOTE_COMPACTION_*` override. The call uses the shared `send-max-retries` (2) and `send-retry-delay`, so the worst case before the silent fallback is about 95 seconds, not the 3-minute `request-timeout` per attempt. `sendAndDecode` takes the timeout as a parameter.
- **Tests.** `CustomerBookFileServiceSpec` (`mock[AIClientDataExtraction]`): compaction used for two or more groups, a result with as many notes as were sent accepted, and the fallback for a `ServiceError`, a defect, an empty result and a longer result; the image, one-group and notes-free multi-group cases expect no `noteCompaction` call. `it/AIClientDataExtractionSpec` (WireMock stubs for success, bad request, error, timeout and malformed; the timeout case shortens `noteCompactionRequestTimeout`) proves the request body, the model, and the decode and failure handling. `CustomerBookFileApiSpec` has one success case with a multi-group fixture whose compaction stub returns a note distinct from the raw notes. A manual golden spec feeds repeated and related notes through the real model, under [gap 14](../acceptance-test-gaps.md#14-address-note-and-processing-message-rules-in-customer-extraction). HTTP cannot trigger the fallback, because the error stubs key off the processing-message token that this call does not send.

`extractFromImage` reads and base64-encodes the scanned path, then sends `Content.ContentPart.ImageUrl` with a `data:<mime>;base64,...` URL to the configured image model. `extractFromCsv` is fully generic: it knows nothing about `CustomerBookFileAIExtract`. It takes the `ZStream[Scope, ServiceError, CSVRecord]` `SpreadsheetTool` produces, indexes it with `.zipWithIndex` (header included, so the header lands at raw index 0), peels the header off, groups the remaining data records into batches of at most `csvBatchMaxDataRows` rows (still always at least one batch) and runs them with `csvBatchParallelism`-bounded concurrency. Each row's real row number (raw index plus one, so the header is row 1) is embedded as an extra leading `Row Number` column, and the header gets a `"Row Number"` label in that column. Blank rows are not filtered out: they consume a slot in the batch window like any other row, and the caller's instructions tell the model how to report them. Each batch goes as `Content.TextContent(text)` to the configured CSV model; one decoded `A` per batch comes back as a `NonEmptyChunk` in batch order; the client merges nothing. When `processingMessageOpt` is present it is sent as a separate, final `Message.User` after the source content, identically for every batch and for images. Both methods share one private `sendAndDecode` helper.

The image path reads the local file once before the send loop; the CSV stream is consumed once, incrementally, as each batch is pulled. Retry policy (three-minute per-attempt timeout, two retries after the first attempt, one-/two-second backoff), schema handling and response decoding are identical for both methods. Each OpenAI send attempt has a three-minute read timeout by default, overridable through `AI_CLIENT_DATA_EXTRACTION_REQUEST_TIMEOUT`. The client makes at most three attempts, waiting one second before the second and two before the third. It retries connection, read and timeout failures plus HTTP `408`, `409`, `429` and `5xx`; it does not retry image-stream read failures, other `4xx` responses (including invalid-schema `400`), OpenAI-envelope deserialization failures, or structured-response JSON/Iron decoding failures. Exhaustion keeps the existing `500 INTERNAL_SERVER_ERROR` with no partial candidates. A read failure can happen after OpenAI processed the request, so a retry can create and charge for a duplicate generation; worst-case waiting time for one request is about nine minutes plus the backoff.


### New dependencies

- **Apache POI** (`poi`, `poi-ooxml`) — parses both `.xls` (HSSF) and `.xlsx` (XSSF); the only maintained JVM library covering both legacy and current Excel formats. Used only inside `SpreadsheetTool`.
- **Apache Commons CSV** — the structural "genuinely readable as CSV" parse gate; avoids hand-rolling RFC4180 quoting/embedded-newline handling.

Both added to `project/Dependencies.scala` with one centralized version each, wired into `build.sbt` the same way `scrimage`/`tika` already are. Also added: a `log4j-to-slf4j` bridge (pinned to match POI's transitive `log4j-api` version), so POI's internal logging routes through this project's normal Logback pipeline instead of falling back to a console `SimpleLogger`.

### Large spreadsheet handling

There is no application-level row limit. Inside `AIClientDataExtraction.extractFromCsv`, CSV and converted Excel data (blank rows included) is divided into groups of at most `csvBatchMaxDataRows` rows, each with the original header and a leading `Row Number` column, before it reaches the model. The client runs at most `csvBatchParallelism` group calls concurrently (defaults 100 and 4); each group is its own `sendAndDecode` call with its own timeout/retry budget, and the whole extraction fails if any group still fails, never returning partial candidates. `CustomerBookFileService` merges the returned chunk once every group has succeeded.

**Accepted trade-off:** the AI response is one structured-output JSON document decoded in a single pass, so a populated field that fails its Iron constraint (names, emails, phone parts, address text, tax id, contact role) fails the entire decode and surfaces as one `500 INTERNAL_SERVER_ERROR` for the whole request. Only the email and enum constraints reach the provider schema (verified in R2); the `NonEmptyTrimmed` rule does not, so a blank, untrimmed or over-255-character string is possible, and the prompts state each constraint explicitly (see the prompt rules). Phone realness and the address combination are not checked in the preview; the exactly-one-default rule cannot fail because the service sets defaults.

### Schema registration

`json/OpenAIJsonSchema.scala` declares `OpenAIJsonSchema[A]`. `json/ai.scala` owns the AI registrations and `ai.fromTapir`: it derives `Schema` bottom-up for `CustomerBookFileAIExtract` and its nested types, adapts it with `fromTapir`, and adds the `JsonCodecMaker` codec.
