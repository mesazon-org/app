# Catalogue

Tenant-scoped products/services sold by the organization.

## Scope

Owns `catalogue_item`: name, free-text unit, optional exact price/currency, optional image metadata, one-way archival, and the image upload endpoint (see [Image upload](#image-upload)) that writes back the three image columns without changing `CatalogueItemStatus`. Excludes orders/line items and tenant membership/roles.

## Model and decisions

`catalogue_item`:

- PK `(organization_id, catalogue_item_id)`; all access is tenant-scoped.
- `name text not null`.
- `unit text not null`: open vocabulary (`piece`, `kg`, `hour`, bespoke services); rejected enum because new units must not require code/migrations.
- `price_amount numeric` + `price_currency text`: both null or both present. The application models them as optional `CatalogueItemPrice`, a `Pure` newtype over `Price` with mandatory amount/currency, so a half-price is unrepresentable. `numeric`/Scala `BigDecimal` is exact; never pass through `Double`. New client input is ISO 4217 only: trim and uppercase the code, resolve it through `java.util.Currency`, and reject unsupported codes or currencies whose fraction digits are `-1`.
- Price validation is shared because amount validity depends on currency. Amounts must be non-negative with at most 12 integer digits (equivalent to `[0, 1,000,000,000,000)`) and their supplied `BigDecimal` scale must satisfy `scale <= currency.getDefaultFractionDigits`; for non-zero amounts, check the integer-digit bound with widened `precision - scale` arithmetic before normalization so a compact extreme exponent cannot cause unbounded allocation. Zero bypasses that representation-derived bound because its exponent does not change its value. Never round or remove supplied precision. After validation, normalize upward to the currency's exact scale by appending zeros. Thus `JPY 1.00` is invalid, `USD 1` becomes `1.00`, `KWD 1.23` becomes `1.230`, zero is valid at any scale, and a non-zero value with a negative scale is valid only within the amount bound and is normalized exactly. Failures are accumulated `InvalidFieldError`s naming field `amount` (negative, more than 12 integer digits, scale above the currency's fraction digits) or `currency` (unknown ISO code, no fixed fraction digits).
- Smithy encodes `BigDecimal` as a JSON number. If clients cannot preserve exact decimal scale, change wire `amount` to `String` and parse it at validation.
- Image columns: `image_original_s3_bucket_key`, `image_normalized_s3_bucket_key`, and `image_original_file_name` are jointly optional. The application models them as optional `CatalogueItemImageAsset`, a `Pure` newtype over `ImageAsset` with mandatory original bucket key, normalized bucket key, and original file name, so partial image metadata is unrepresentable. Mirrors the organization-logo upload pipeline (see [Organization Management](organization-management.md#logo-upload)), which builds the same shared `ImageAsset`/`ImageOriginalS3BucketKey`/`ImageNormalizedS3BucketKey`/`ImageOriginalFileName` value newtypes into its own contextual `OrganizationLogoImageAsset` wrapper. Insert/update contain no bytes; GET models expose presigned URL fields, generated on the fly from the stored bucket keys.
- `status catalogue_item_status` (`Active|Archived`): native PG enum matching Scala case names. Never hard-delete; no unarchive.
- `uq_catalogue_item_name`: partial unique `(organization_id, name) where status='Active'`; archive frees names. Repository maps its `23505` to 409.

The `numeric` choice is the documented exception to the usual primitive set.

## Endpoints

`CatalogueService`: bearer + completed onboarding + `X-Organization-ID`. Reads allow `Owner|Admin|User`; writes `Owner|Admin`.

| Method | Path | Operation | Effect/result |
|---|---|---|---|
| POST | `/insert/catalogue-item` | `InsertCatalogueItemPost` | create active item |
| POST | `/insert/catalogue-items` | `InsertCatalogueItemsPost` | atomic batch |
| PUT | `/update/catalogue-item` | `UpdateCatalogueItemPut` | update name/unit/price |
| PUT | `/archive/catalogue-item` | `ArchiveCatalogueItemPut` | archive by ID |
| GET | `/get/catalogue-item/{catalogueItemID}` | `GetCatalogueItemGet` | full item: name, unit, price, normalized image URL only |
| GET | `/get/catalogue-items` | `GetCatalogueItemsGet` | active-item summaries: name, status, normalized image URL only — no unit/price |

Errors:

- insert/update: `BadRequest, ValidationError, Unauthorized, Forbidden, Conflict, InternalServerError`.
- archive/read: `BadRequest, Unauthorized, Forbidden, InternalServerError`; pure UUID cannot validation-fail and archive cannot create a name conflict.
- Organization gate (all six, per [Authentication](../project/authentication.md#organization-scope)): missing `X-Organization-ID` → 400 `BAD_REQUEST_ERROR`; no membership row → 500 `INTERNAL_SERVER_ERROR`, not 403; disallowed role → 403; missing user details → 500. `CatalogueApiSpec` proves the non-member and missing-details 500s on every endpoint.

Contract: `smithy/CatalogueService.smithy`, `smithy/domain/Catalogue.smithy`. Optional `price` is `CatalogueItemPriceRequest`; if present, both `amount` and `currency` are required. Request lists use `@default([])`; response lists use `@required`. `CatalogueItemStatus` is a Smithy enum (`Active`/`Archived`) exposed only on the list response; `GatewayClient`'s jsoniter codec for it must be hand-written like `OnboardStage`/`CustomerType` — smithy4s enums are not native Scala 3 enums, so macro derivation silently produces the wrong wire shape without one.

## Image upload

`POST /upload/catalogue-item/image` is a Tapir streaming endpoint, not Smithy — Smithy JSON routes cap at 5 MB (`HttpApp.SmithyMaxEntitySize`); Tapir streams binary and allows 20 MB (`HttpApp.TapirMaxEntitySize`, kept equal to `file-service.file-bytes-max`). See [Alternate HTTP](../project/alternate-http.md) for the shared Tapir transport mechanics (docs mounting, error model, security wiring) this endpoint follows alongside [Organization Management](organization-management.md#logo-upload)'s logo upload — the two mirror the same pipeline shape, differing only in entity scoping and persistence target.

Binary body; organization in `X-Organization-ID`, catalogue item in `X-Catalogue-Item-ID`, original file name in `X-File-Name`. Security (`AuthorizationService.auth`): valid access JWT, `OnboardStage.completedStages` (= `PhoneVerified`), and the caller must be assigned to the organization as `Owner` or `Admin` (disallowed role → `403`, no membership row → `500`).

Errors: `TapirServerError` has no validation variant, so every 400 here is `BAD_REQUEST_ERROR` (never `VALIDATION_ERROR`). `HttpErrorHandler.errorResponseHandlerTapir` maps every `ServiceError.BadRequestError` — including `FileScanner`'s `ValidationError` for a missing/unsupported extension or an extension/detected-content mismatch — to `TapirServerError.BadRequestError`; a missing or undecodable `X-Organization-ID`/`X-Catalogue-Item-ID`/`X-File-Name` header goes through `tapir.scala`'s decode-failure handler, also `400 BAD_REQUEST_ERROR`. Missing/archived/foreign item, image decode/processing failure, and over-cap bytes are `500 INTERNAL_SERVER_ERROR`.

`FileService.uploadCatalogueItemImage` runs inside one `ZIO.scoped` block; every intermediate file is a `TempFile.createScoped` (auto-deleted on scope close, even on failure):

1. Load the catalogue item (`CatalogueRepository.getCatalogueItem`) and fail with `InternalServerError` if it's missing or not `Active` (archived items keep their existing image, if any, untouched) — checked before any bytes are read.
2. `FileScanner.scan` validates the existing declared filename header, spools the incoming `ZStream[Byte]` to a temp file, and drains the entire input even past the byte cap (writing at most `fileBytesMax + 1` bytes, discarding the rest) so an oversized request body isn't abandoned mid-read (rationale: [Streaming uploads](../project/streaming-uploads.md)). It detects the actual MIME type with Apache Tika using the filename as a hint, requires the extension and detected MIME to agree, and rejects anything outside `SupportedMediaType.images` (`PNG`, `JPEG`, `WEBP`).
3. `ImageProcessing.normalize` re-detects the format with scrimage's `FormatDetector`, decodes, bounds to 640×640 px (`MaxDimensionPixels`), and re-encodes as lossless WebP. Yields the untouched original stream and the normalized variant.
4. `S3ClientOrganizationMedia.uploadImage` stores both variants at `{catalogueItemImageBucketPathPrefix}/{organizationID}/{catalogueItemID}/{originalFileName|normalizedFileName}` in bucket `organization-media`, returning both bucket keys as an `UploadedImageResult` (`imageOriginalS3BucketKey`/`imageNormalizedS3BucketKey`), from which the service builds a `CatalogueItemImageAsset` (composite `ImageAsset` newtype: original bucket key, normalized bucket key, original file name). `genMediaUrl` takes a single `S3BucketKey` and returns a presigned GET URL (`urlExpiresAtOffset`) as `S3MediaUrl`, shared for both original and normalized variants and across every kind of organization-owned media the client serves — catalogue-item images and (see [Organization Management](organization-management.md#logo-upload)) organization logos alike; images are never served through the gateway. `readiness` does a `HeadBucket` check for the health endpoint.
5. `CatalogueRepository.updateCatalogueItem`'s `imageAssetOptUpdate` persists the `CatalogueItemImageAsset`. `CatalogueItemStatus` is untouched — unlike the logo upload, this endpoint never transitions the owning row's lifecycle state.

## Completed proof

`PriceDomainValidatorSpec` proves ISO normalization, canonical upward scale normalization, the exclusive monetary upper bound, compact non-zero extreme-exponent rejection, extreme-scale zero acceptance, fixed-fraction boundaries for zero-, two-, and three-digit currencies, pseudo/unsupported currency rejection, negative amounts, zero, and bounded non-zero negative scales. `CatalogueRequestValidatorSpec` proves success round-trips and exact accumulated errors for single insert, indexed batch insert, and update, including absent optional prices.

`CatalogueRepositorySpec` covers every repository method against real PostgreSQL: controlled IDs/timestamps and complete rows sampled from repository arbitraries; absent/present exact ISO-valid prices from the shared correlated generator; absent creation image metadata and composite image updates; tenant scope; active-name conflicts and exact error mapping; batch order, no-op, and rollback; update/no-op semantics; archive/name reuse; active-and-archived reads; and active-only unordered listing of `CatalogueItemSummaryRow`.

## Acceptance proof

`CatalogueApiSpec` follows [Acceptance testing](../project/acceptance-testing.md) and covers all six endpoints over the real gateway and PostgreSQL stack. It proves complete rows/responses, exact validation and conflict bodies, atomic batch rollback and empty batches, update/archive no-ops for missing, archived, or foreign-organization items, archived by-ID visibility, active-only tenant-filtered listing, persisted image-field mapping, and every applicable organization middleware branch. ## Service implementation

`CatalogueService` validates insert/update bodies, maps validated requests into repository-owned insert inputs, preserves the organization ID on every repository call, and maps rows back to Smithy responses. Missing catalogue-item reads become `InternalServerError` with the stable `catalogueItemID` message. Update and archive remain silent `204` no-ops for missing or archived items, matching the repository's active-row mutation semantics.

Both GET operations depend on `S3ClientOrganizationMedia.genMediaUrl` to resolve a real presigned URL from the persisted normalized bucket key — `getCatalogueItemGet` and `getCatalogueItemsGet` each resolve only `imageNormalizedUrl` (`Option[String]`, absent when the item has no image); the original bucket key is persisted (for migrations and user download) but never resolved to a URL in either response. `getCatalogueItemsGet` resolves it per item via `ZIO.foreach` over the repository's `CatalogueItemSummaryRow` list.

`CatalogueServiceSpec` uses real price validation, a strict `CatalogueRepository` mock, and a strict `S3ClientOrganizationMedia` mock. It proves each of the six operations' mapping and response behavior, validation isolation, missing-item policy, no-op mutations, unchanged repository failures, and both the with-image and without-image branches of the GET endpoints' presigned-URL resolution.

Attributes, selling unit, and status are plain `Option[X]`: replaced whole, never cleared.

### Validation

- Staging request types live in `CatalogueV2.scala` and `CatalogueV2RequestValidator` so the live V1 requests remain unchanged. The shared typed-currency `PriceValidator` validates `Price`, and the V2 request validator wraps it in `CatalogueItemVariantPrice`. The V2 request validator handles the single insert, batch insert, item update, and name/SKU uniqueness check; archive and ID-only reads need no request validator. At cutover the staging request validator takes the canonical Catalogue name.
- V2 variant price uses `PriceValidator`, separate from V1's free-text ISO `PriceDomainValidator`; V1 keeps its ISO currency behavior until cutover. V2 accepts only the exact uppercase codes `EUR`, `USD`, and `GBP`, without trimming or case conversion. Amounts are non-negative, have at most 12 integer digits and at most two decimal places on input, and are stored at exactly two decimal places by appending zeros; never round. Guard the integer-digit check against compact extreme exponents before calling `setScale`.
- Quantity, per-unit, and unit-size values are each greater than 0 and at most 99,999; validation preserves their supplied decimal places without rounding or a separate scale cap. Extremely precise values can pass validation yet exceed PostgreSQL `jsonb`'s numeric range when persisted; this is a known cutover risk accepted for this rule.
- `CatalogueV2RequestValidator` validates selling-unit quantity, per-unit, and unit-size values directly, mapping their closed Smithy enums through Chimney and accumulating invalid numbers in field order. Its spec covers all unit cases, optional parts, exact decimal preservation, boundaries, and ordered errors. Variant prices delegate to `PriceValidator`.
- Insert item: at least one variant. The validated `CatalogueItemPostRequest.variants` is a `NonEmptyChunk`, built by shared `validateNonEmptyNested`; an empty input reports `InvalidFieldError("variant", "At least one variant must be provided", Seq.empty)`. Update `variantsInsert` entries: selling unit required (Smithy `@required`); price optional, as on insert (absent = no set price). Update rejects every status in `CatalogueItemVariantStatus.disabled` (currently `Archived`).
- Error naming: indexed variant errors and the empty-variant error both use `variant`; batch nests under `catalogueItem`. Each error names the item index, then the variant index, then the field.
- Uniqueness: when both optional query fields are absent, return two ordered `InvalidFieldError`s, one for `name` and one for `sku`, each with an empty submitted-value list and the at-least-one-required message. Supplied invalid values retain their own field errors.
- The three unit fields and `currency` are closed Smithy enums on the wire, so an unknown unit or currency is a decode-time 400 that names neither the item nor the variant. Variant `status` in update is the full four-case Smithy enum; `Archived` is rejected by the validator.
- `PriceValidatorSpec` proves typed currency, monetary boundaries, and exact scale. `CatalogueV2RequestValidatorSpec` proves each fallible request's round-trip and ordered error accumulation, including variant and batch indexes. The shared `Price` arbitrary generates valid EUR, USD, and GBP prices; both catalogue price wrappers reuse it. V1's ISO validator behavior remains unchanged and its explicit tests still cover other currencies.

- Enums: `CatalogueItemVariantStatus` (four cases); `CatalogueItemVariantUnit` (all 15 unit cases, for `quantity.unit`); `CatalogueItemVariantUnitUnitSize` (8) and `CatalogueItemVariantUnitPerUnit` (5) for `unitSize.unit`/`perUnit.unit`. Smithy has no sealed-trait-of-enums, so the combined enum flattens the domain's three groups while the narrow enums mirror `CatalogueItemVariantUnit.UnitSize`/`.PerUnit`; the wire stays a plain unit string.
- Value shapes reused by requests and responses, so they carry no `Request` suffix: `CatalogueItemVariantPrice{amount: BigDecimal, currency: String}`, `CatalogueItemVariantSaleUnit{quantity (required), perUnit, unitSize}`, `CatalogueItemVariantQuantity`/`CatalogueItemVariantPerUnit`/`CatalogueItemVariantUnitSize{value: BigDecimal, unit}`, `map CatalogueItemVariantAttributes {String: String}`.
- Name collisions with the domain (intended): each of these value shapes has exactly the name of its domain counterpart in `io.mesazon.domain.gateway`. `CatalogueItemVariantPrice` is the `Pure[Price]` newtype in `Newtypes.scala`. `CatalogueItemVariantSaleUnit`, `CatalogueItemVariantQuantity`, `CatalogueItemVariantPerUnit`, and `CatalogueItemVariantUnitSize` are case classes in `CatalogueItemVariantSaleUnit.scala`. Generated types stay package-qualified (`smithy.v2.CatalogueItemVariantPrice` vs bare domain `CatalogueItemVariantPrice`), and where both are bound, the generated binding takes the `Smithy` suffix per [Smithy names](../standards/smithy.md#names). The two narrow enums are named `CatalogueItemVariantUnit…` so they do not take the case-class names.
- Insert: `CatalogueItemPostRequest{name, description, variants: CatalogueItemVariantsInsert}`; `CatalogueItemVariantInsert{sku, label, description, attributes @default({}), price, sellingUnit (required)}`, no status (the service stores `Active`). Batch `CatalogueItemBatchPostRequest{catalogueItems: CatalogueItemsInsert}`, a list of `CatalogueItemPostRequest`. Responses return the created IDs: `CatalogueItemPostResponse{catalogueItemID}` and `CatalogueItemBatchPostResponse{catalogueItemIDs}`, the latter in request order (the repository's `NonEmptyChunk[CatalogueItemID]` order). `list CatalogueItemIDs` (UUID) serves both this response and the summary read's `catalogueItemIDs` query parameter.
- Update: `CatalogueItemPutRequest{name, description @nullable, variantsUpdate, variantsInsert}` (`catalogueItemID` is the path label; both lists `@default([])`); `variantsUpdate: CatalogueItemVariantsUpdate` of `CatalogueItemVariantUpdate{catalogueItemVariantID (required), sku/label/description/price @nullable, attributes, sellingUnit, status}`; `variantsInsert` reuses `CatalogueItemVariantsInsert`, the create entry list, so it carries no `status` and the service stores `Active`. `@alloy#nullable` generates `Option[Nullable[X]]`: absent keeps, `null` clears. `attributes` has no default: absent keeps, `{}` clears all.
- Archive: no body or request shape; `catalogueItemID` (and `catalogueItemVariantID`) are path labels.
- Detail: `CatalogueItemGetResponse{catalogueItemID, name, description, status, imageNormalizedUrl, variants: CatalogueItemVariants}`; `CatalogueItemVariant{catalogueItemVariantID, sku, label, description, attributes (required), price, sellingUnit (required), status (required)}`.
- Summaries: `CatalogueItemSummaryGetResponse.catalogueItemSummaries: CatalogueItemSummaries` of `CatalogueItemSummary{catalogueItemID, name, status, imageNormalizedUrl, variants: CatalogueItemVariantSummaries (required)}` with `CatalogueItemVariantSummary{catalogueItemVariantID (required), sku, label, price, sellingUnit (required), status (required)}`. Service branching (future slice): empty `catalogueItemIDs` calls `getAllCatalogueItemSummariesEnabled`; non-empty converts to `NonEmptyChunk` and calls `getCatalogueItemSummariesEnabled`. They mirror `CatalogueItemSummaryRowV2`/`CatalogueItemVariantSummaryRow` 1:1, carrying only enabled variants in repository order; `imageNormalizedUrl` is the presigned URL resolved from `imageAsset`. No from-prices or variant count is computed server-side; the epic still describes them (open PO gap). The price and selling-unit value shapes are shared value shapes.
- Uniqueness check: optional query params `name` and `sku`, each checked on its own; either or both may be given. `CatalogueItemUniquenessGetResponse{isNameUnique, isSkuUnique}`, both optional `Boolean`, each present only when its param was given. Backed by `CatalogueRepositoryV2.isUniqueCatalogueItemName`/`isUniqueCatalogueItemVariantSKU`, called only for the given params. Same scope as the partial unique indexes: a name is taken only by an `Active` item (`uq_catalogue_item_name`), a SKU only by a non-`Archived` variant (`uq_catalogue_item_variant_sku`, case-sensitive); archived items/variants never count. The check reserves nothing; a later insert/update can still hit the 409. Query values are raw `String` on the wire; the validator refines them to `CatalogueItemName`/`CatalogueItemVariantSku`.
- Request lists `@default([])`; response lists and maps `@required`.

`GatewayClient`: hand-written jsoniter codecs for every new enum (like `OnboardStage`/`CustomerType`), a hand-written null-emitting codec for the nullable members (new pattern), and encoding that keeps `attributes: {}` on update so clearing all attributes is possible.

### Repository and transactions

- `CatalogueQueries` contains the V2 item and variant queries; `CatalogueRepositoryV2Spec` exercises them against PostgreSQL.
- `CatalogueItemRowV2` has `description` instead of V1's `unit`/price; `CatalogueItemVariantRow` stores optional price and the JSONB selling unit.
- Insert (single and batch): item plus its variants in one transaction, all-or-nothing; variants start `Active`.
- `updateCatalogueItem(organizationID, catalogueItemID, nameOptUpdate, descriptionOptUpdate, imageAssetOptUpdate, updateCatalogueItemVariantInputs, insertCatalogueItemVariantInputs)` is the single item update; there is no separate image-asset method, so `FileService` calls it with only `imageAssetOptUpdate` set and empty variant lists. One transaction. It first runs the item `UPDATE` filtered to `CatalogueItemStatus.enabled` (currently only `Active`); that `UPDATE` takes the item row lock implicitly (no explicit `SELECT ... FOR UPDATE`; `CatalogueRepositoryV2Spec` proves it serializes two concurrent updates of the same variant, so neither change is lost), and 0 affected rows (item missing, archived, or in another organization) means silent no-op success, even with bogus variant IDs. Every named variant must exist, belong to this item, and be non-archived; one query fetches the named variants scoped to the item and `CatalogueItemVariantStatus.enabled` (`Active`, `Inactive`, `OutOfStock`), and if fewer come back than were requested, the repository fails before any variant write (the transaction rolls back the item `UPDATE`) with a single `InternalServerError.UnexpectedError` whose message names the item ID, the requested variant IDs, and the enabled variant rows found (the three causes — missing, another item's, archived — are not distinguished). Then apply the item and variant changes and insert `Add` variants with the given status (default `Active`).
- `archiveCatalogueItem`: one transaction. The item `UPDATE` to `Archived`, filtered to `CatalogueItemStatus.enabled`, is both the gate and the implicit item row lock (same mechanism as `updateCatalogueItem`). 0 affected rows (missing, already archived, or another organization) is a silent no-op. Otherwise every variant of the item in `CatalogueItemVariantStatus.enabled` is set `Archived` with the same `updatedAt`; already-archived variants keep their `updatedAt`. Errors map to `InternalServerError.RepositoryError` (status-only, no unique constraint). `CatalogueRepositoryV2Spec` covers the cascade, the untouched already-archived variant and sibling item, each no-op leaving the item's variants untouched, and an `archiveCatalogueItem`/`updateCatalogueItem` race (archive in parallel with an update adding a variant) proving the item never ends archived with an enabled variant.
- `archiveCatalogueItemVariant`: one transaction. It first locks the item row with `SELECT ... FOR NO KEY UPDATE` filtered to `CatalogueItemStatus.enabled` — the same lock mode the item `UPDATE` in `updateCatalogueItem`/`archiveCatalogueItem` takes, but without bumping the item's `updatedAt`. No row (item missing, archived, or another organization) is a silent no-op. Then it reads the item's `CatalogueItemVariantStatus.enabled` variant IDs; because every variant-mutating transaction holds that item lock, this view cannot change before the decision. Target not among them (missing, another item's, already archived) is a silent no-op. Target is the only enabled variant: fail with `ForbiddenError.InvalidAction("archiveCatalogueItemVariant", ...)` (403), nothing changes, and the item is never archived by this path — archive the item instead. Otherwise the target alone is set `Archived` with a new `updatedAt`; `Inactive`/`OutOfStock` siblings count as enabled. Other errors map to `InternalServerError.RepositoryError`. `CatalogueRepositoryV2Spec` covers the success, rejection, and every no-op case, plus a race of two concurrent archives of an item's last two enabled variants, proving exactly one succeeds and the other gets `InvalidAction`.
- Every mutating variant transaction locks the item row first, so concurrent archives cannot leave an active item with no non-archived variants, or active variants on an archived item.
- `getCatalogueItemWithVariantsActive(organizationID, catalogueItemID)` → `Option[CatalogueItemWithVariantsRow]` (item row + `NonEmptyChunk` of variant rows): one SQL statement, item `INNER JOIN` variant on `(organization_id, catalogue_item_id)`, selecting only the explicitly listed, alias-qualified columns both rows need (the variant's `organization_id`/`catalogue_item_id` are not re-selected; they come from the item). The item must be in `CatalogueItemStatus.enabled` and the variants in `CatalogueItemVariantStatus.enabled`, so archived variants are never returned. Variants are ordered oldest first: `created_at ASC`, then `catalogue_item_variant_id ASC` (UUIDv7) as a tiebreaker, because variants inserted together share one `created_at`. `None` when the item is missing, archived, or in another organization. An active item with no enabled variants also gives `None`, because the `INNER JOIN` matches nothing; the write paths already prevent that state. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositoryV2Spec` covers the success case (exact oldest-first order with variants inserted out of order; archived and sibling-item variants excluded), each `None` case, and the only-archived-variants case.
- `getAllCatalogueItemSummariesEnabled(organizationID)` → `List[CatalogueItemSummaryRowV2]` (`catalogueItemID`, `name`, `imageAsset`, `status`, plus a `NonEmptyChunk` of `CatalogueItemVariantSummaryRow`: `catalogueItemVariantID`, `sku`, `label`, `price`, `sellingUnit`, `status`): one SQL statement, item `INNER JOIN` variant on `(organization_id, catalogue_item_id)`, selecting only the alias-qualified columns those two summary rows need (no `organization_id`, item `description`, variant `description`/`attributes`, or timestamps). Only items in `CatalogueItemStatus.enabled` and variants in `CatalogueItemVariantStatus.enabled` are returned, so disabled items and disabled variants never appear; there is no paging or filtering. Order is contractual: items oldest first (`i.created_at ASC`, then `i.catalogue_item_id ASC`), and each item's variants oldest first (`v.created_at ASC`, then `v.catalogue_item_variant_id ASC`), because batch-inserted rows share one `created_at`. `created_at` orders rather than name or ID alone, since PostgreSQL's collation and byte-wise UUID comparison do not match Scala's ordering, so tests could not state the expected order. The joined rows are grouped by `catalogueItemID` in Scala, keeping SQL order. An enabled item with no enabled variants matches nothing in the `INNER JOIN` and is left out; the write paths already prevent that state. The repository returns raw enabled variant rows, and `CatalogueItemSummaryGet` returns them as variant summaries; no from-prices or variant count is computed. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositoryV2Spec` covers the success case (exact item and variant order with rows inserted out of order; disabled variants, a disabled item, and another organization's item excluded), the empty organization, the only-disabled-items case, and an enabled item with only disabled variants being left out.
- `getCatalogueItemSummariesEnabled(organizationID, catalogueItemIDs: NonEmptyChunk[CatalogueItemID])` → `List[CatalogueItemSummaryRowV2]`: the same query as `getAllCatalogueItemSummariesEnabled` (shared private helper in `CatalogueQueries`, same join, columns, enabled filters, contractual created-first ordering, and Scala grouping) plus `i.catalogue_item_id IN (...)`. Request order and duplicates in `catalogueItemIDs` do not affect the result; it follows the item `created_at` order. Requested IDs that match no enabled item with at least one enabled variant (missing, disabled, in another organization, or with only disabled variants) are simply absent, never an error. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositoryV2Spec` covers the success case (exact order with IDs requested in reverse and rows inserted out of order; disabled variants and an unrequested enabled item excluded), a requested disabled item, requested missing and other-organization IDs, a requested item with only disabled variants, and no requested ID matching.
- Reads: V2 provides `getCatalogueItemWithVariantsActive` and the all/selected enabled-summary queries described above.
- Unique mapping adds `uq_catalogue_item_variant_sku` → 409.
