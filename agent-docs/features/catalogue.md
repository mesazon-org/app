# Catalogue

Organization-scoped items with variants, exact prices, selling units, and item images. Orders, paging/search, unarchive, and variant-specific images remain outside this feature.

## Schema

Edited in place in `V2025.05.27__init.sql`; no new migration, no data migration. Dev Flyway runs `clean, migrate`.

`catalogue_item`: PK `(organization_id, catalogue_item_id)`; `name text not null`, optional `description`, jointly optional image metadata, `status catalogue_item_status` (`Active`, `Archived`), and required `created_at`/`updated_at` timestamps. `uq_catalogue_item_name` is partial unique `(organization_id, name) where status = 'Active'`; archiving frees the name. The parent has no unit or price columns. Image metadata is the jointly optional original key, normalized key, and original filename, represented by `CatalogueItemImageAsset` over `ImageAsset`. All access is organization-scoped.

`catalogue_item_variant`:

- `organization_id uuid`, `catalogue_item_variant_id uuid`, `catalogue_item_id uuid`, PK `(organization_id, catalogue_item_variant_id)` so a variant can be found by ID alone (needed to detect "belongs to another item").
- FK `(organization_id, catalogue_item_id)` → `catalogue_item` `on delete restrict`; `idx_catalogue_item_variant_item` on `(organization_id, catalogue_item_id)`.
- `sku`, `label`, `description` nullable `text`; `attributes jsonb not null` (JSON object, name → value).
- `price_amount numeric` and `price_currency text` are jointly optional, enforced by `chk_catalogue_item_variant_price`.
- `selling_unit jsonb not null` stores the quantity, optional per-unit part, and optional unit-size part. The domain and validator enforce their value and unit rules.
- `status catalogue_item_variant_status not null`: native PG enum (`Active`, `Inactive`, `OutOfStock`, `Archived`), the same documented exception as `catalogue_item_status`; qualified casts as for the item.
- `created_at`, `updated_at timestamptz not null`.
- `uq_catalogue_item_variant_sku`: partial unique `(organization_id, sku) where status <> 'Archived' and sku is not null`; case-sensitive; mapped to 409, including duplicates within one request.
- Config: `RepositoryConfig.catalogueItemVariantTable` + `allTableNames` and both `application.conf` files are updated.

## Domain

- Enums: `CatalogueItemVariantStatus` (`Active`, `Inactive`, `OutOfStock`, `Archived`); `CatalogueItemStatus` stays `Active`/`Archived`. `CatalogueItemVariantUnit` is a sealed trait over three enums: `UnitSize` (`Gram`, `Kilogram`, `Millilitre`, `Litre`, `Millimetre`, `Centimetre`, `Metre`, `SquareMetre`), `PackageUnit` (`Pack`, `Box`), `PerUnit` (`Bag`, `Bottle`, `Can`, `Jar`, `Piece`).
- Price: `Price(amount: PriceAmount, currency: Currency)` stores an exact decimal and the typed currency enum. `PriceValidator` preserves the supplied enum and applies its decimal-place rule. The shared arbitrary reuses `arbCurrency`; Smithy transformations derive mirrored enums directly, and persistence reuses the generic enum-as-text codecs for `price_currency`. Owner wrapper `CatalogueItemVariantPrice` (`Pure[Price]`), optional on a variant.
- Selling unit (required on every variant): `CatalogueItemVariantSaleUnit(quantity: CatalogueItemVariantQuantity, perUnit: Option[CatalogueItemVariantPerUnit], unitSize: Option[CatalogueItemVariantUnitSize])`. `CatalogueItemVariantQuantity(value, unit: CatalogueItemVariantUnit)` takes any unit; `CatalogueItemVariantPerUnit(value, unit: CatalogueItemVariantUnit.PerUnit)` and `CatalogueItemVariantUnitSize(value, unit: CatalogueItemVariantUnit.UnitSize)` are restricted. The three value newtypes are `BigDecimal` refined `Positive & LessEqual[99999]`.
- Newtypes (Catalogue group): `CatalogueItemDescription`, `CatalogueItemVariantID`, `CatalogueItemVariantSku`, `CatalogueItemVariantLabel`, `CatalogueItemVariantDescription`, `CatalogueItemVariantAttributeName`, `CatalogueItemVariantAttributeValue` (text ones `NonEmptyTrimmed`), `CatalogueItemVariantQuantityValue`, `CatalogueItemVariantPerUnitValue`, `CatalogueItemVariantUnitSizeValue`.
- Attributes: free-form `Map[CatalogueItemVariantAttributeName, CatalogueItemVariantAttributeValue]`, no fixed vocabulary. Duplicate JSON keys are resolved last-wins by the decoder, so names are unique by type; duplicates in the raw body are not rejected.
- Update: the wire carries two lists, mirroring `CatalogueRepository.updateCatalogueItem`: `variantsUpdate` changes existing variants (each names its `catalogueItemVariantID`) and maps to `UpdateCatalogueItemVariantInput`; `variantsInsert` adds variants (full payload, no ID, no status: always stored `Active`, as on create) and maps to `InsertCatalogueItemVariantInput`. The response stays empty; a client needing the new variant IDs re-reads `GET /catalogue/item/{catalogueItemID}`. Clearable fields (item description; variant SKU, label, description, price) are `Option[Option[X]]`: outer `None` keeps, `Some(None)` clears. Attributes, selling unit, and status are plain `Option[X]`: replaced whole, never cleared.

## Validation

- Request types live in `Catalogue.scala`; `CatalogueRequestValidator` validates single insert, batch insert, item update, and name/SKU uniqueness. Archive and ID-only reads need no request validator. Shared `PriceValidator` validates `Price`, then the feature validator wraps it in `CatalogueItemVariantPrice`.
- Prices accept only exact uppercase Smithy currency codes `EUR`, `USD`, and `GBP`, without trimming or case conversion. `Currency.decimalPoints: Option[Int]` is `Some(2)` for these cases: reject supplied scales above two and append zeros to exactly two stored places, without rounding. A future `None` case has no scale restriction and preserves the amount. Amounts remain non-negative with at most 12 integer digits. For non-zero amounts, compare widened `precision - scale` before normalization to avoid allocating a compact extreme exponent; zero bypasses that representation-derived bound.
- Quantity, per-unit, and unit-size values are each greater than 0 and at most 99,999; validation preserves their supplied decimal places without rounding or a separate scale cap. Extremely precise values can pass validation yet exceed PostgreSQL `jsonb`'s numeric range when persisted; this is a known storage risk accepted for this rule.
- `CatalogueRequestValidator` validates selling-unit quantity, per-unit, and unit-size values directly, mapping their closed Smithy enums through Chimney and accumulating invalid numbers in field order. Its spec covers all unit cases, optional parts, exact decimal preservation, boundaries, and ordered errors. Variant prices delegate to `PriceValidator`.
- Insert item: at least one variant. The validated `CatalogueItemPostRequest.variants` is a `NonEmptyChunk`, built by shared `validateNonEmptyNested`; an empty input reports `InvalidFieldError("variant", "At least one variant must be provided", Seq.empty)`. Update `variantsInsert` entries: selling unit required (Smithy `@required`); price optional, as on insert (absent = no set price). Update rejects every status in `CatalogueItemVariantStatus.disabled` (currently `Archived`).
- Batch insert: at least one catalogue item. `CatalogueItemBatchPostRequest.catalogueItems` is a `NonEmptyChunk`, built by `validateNonEmptyNested("catalogueItem", ...)`; empty or omitted wire lists produce `InvalidFieldError("catalogueItem", "At least one catalogueItem must be provided", Seq.empty)`. Non-empty input retains item order and accumulated nested item/variant errors. Domain and Smithy arbitraries follow the same non-empty invariant.
- Error naming: indexed variant errors and the empty-variant error both use `variant`; batch nests under `catalogueItem`. Each error names the item index, then the variant index, then the field.
- Uniqueness: when both optional query fields are absent, return two ordered `InvalidFieldError`s, one for `name` and one for `sku`, each with an empty submitted-value list and the at-least-one-required message. Supplied invalid values retain their own field errors.
- The three unit fields and `currency` are closed Smithy enums on the wire, so an unknown unit or currency is a decode-time 400 that names neither the item nor the variant. Variant `status` in update is the full four-case Smithy enum; `Archived` is rejected by the validator.
- `PriceValidatorSpec` proves typed currency, monetary boundaries, and exact scale. `CatalogueRequestValidatorSpec` proves each fallible request's round-trip and ordered error accumulation, including variant and batch indexes. The shared `Price` arbitrary generates valid EUR, USD, and GBP prices; `CatalogueItemVariantPrice` reuses it.
- Domain validation errors preserve nested item/variant indexes and messages. The current HTTP error handler exposes only their ordered `fieldName` strings in `ValidationError.fields`; detailed nesting is not a claim about the HTTP payload.

## Repository and transactions

- `CatalogueQueries` contains the item and variant queries; `CatalogueRepositorySpec` exercises them against PostgreSQL.
- `CatalogueItemRow` stores name, description, image metadata, status, and audit fields; `CatalogueItemVariantRow` stores optional price and the JSONB selling unit.
- Insert (single and batch): item plus its variants in one transaction, all-or-nothing; variants start `Active`.
- `updateCatalogueItem(organizationID, catalogueItemID, nameOptUpdate, descriptionOptUpdate, imageAssetOptUpdate, updateCatalogueItemVariantInputs, insertCatalogueItemVariantInputs)` is the single item update; there is no separate image-asset method, so `FileService` calls it with only `imageAssetOptUpdate` set and empty variant lists. One transaction. It first runs the item `UPDATE` filtered to `CatalogueItemStatus.enabled` (currently only `Active`); that `UPDATE` takes the item row lock implicitly (no explicit `SELECT ... FOR UPDATE`; `CatalogueRepositorySpec` proves it serializes two concurrent updates of the same variant, so neither change is lost), and 0 affected rows (item missing, archived, or in another organization) means silent no-op success, even with bogus variant IDs. Every named variant must exist, belong to this item, and be non-archived; one query fetches the named variants scoped to the item and `CatalogueItemVariantStatus.enabled` (`Active`, `Inactive`, `OutOfStock`), and if fewer come back than were requested, the repository fails before any variant write (the transaction rolls back the item `UPDATE`) with a single `InternalServerError.UnexpectedError` whose message names the item ID, the requested variant IDs, and the enabled variant rows found (the three causes — missing, another item's, archived — are not distinguished). Then apply the item and variant changes and insert `Add` variants with the given status (default `Active`).
- `archiveCatalogueItem`: one transaction. The item `UPDATE` to `Archived`, filtered to `CatalogueItemStatus.enabled`, is both the gate and the implicit item row lock (same mechanism as `updateCatalogueItem`). 0 affected rows (missing, already archived, or another organization) is a silent no-op. Otherwise every variant of the item in `CatalogueItemVariantStatus.enabled` is set `Archived` with the same `updatedAt`; already-archived variants keep their `updatedAt`. Errors map to `InternalServerError.RepositoryError` (status-only, no unique constraint). `CatalogueRepositorySpec` covers the cascade, the untouched already-archived variant and sibling item, each no-op leaving the item's variants untouched, and an `archiveCatalogueItem`/`updateCatalogueItem` race (archive in parallel with an update adding a variant) proving the item never ends archived with an enabled variant.
- `archiveCatalogueItemVariant`: one transaction. It first locks the item row with `SELECT ... FOR NO KEY UPDATE` filtered to `CatalogueItemStatus.enabled` — the same lock mode the item `UPDATE` in `updateCatalogueItem`/`archiveCatalogueItem` takes, but without bumping the item's `updatedAt`. No row (item missing, archived, or another organization) is a silent no-op. Then it reads the item's `CatalogueItemVariantStatus.enabled` variant IDs; because every variant-mutating transaction holds that item lock, this view cannot change before the decision. Target not among them (missing, another item's, already archived) is a silent no-op. Target is the only enabled variant: fail with `ForbiddenError.InvalidAction("archiveCatalogueItemVariant", ...)` (403), nothing changes, and the item is never archived by this path — archive the item instead. Otherwise the target alone is set `Archived` with a new `updatedAt`; `Inactive`/`OutOfStock` siblings count as enabled. Other errors map to `InternalServerError.RepositoryError`. `CatalogueRepositorySpec` covers the success, rejection, and every no-op case, plus a race of two concurrent archives of an item's last two enabled variants, proving exactly one succeeds and the other gets `InvalidAction`.
- Every mutating variant transaction locks the item row first, so concurrent archives cannot leave an active item with no non-archived variants, or active variants on an archived item.
- `getCatalogueItemWithVariantsActive(organizationID, catalogueItemID)` → `Option[CatalogueItemWithVariantsRow]` (item row + `NonEmptyChunk` of variant rows): one SQL statement, item `INNER JOIN` variant on `(organization_id, catalogue_item_id)`, selecting only the explicitly listed, alias-qualified columns both rows need (the variant's `organization_id`/`catalogue_item_id` are not re-selected; they come from the item). The item must be in `CatalogueItemStatus.enabled` and the variants in `CatalogueItemVariantStatus.enabled`, so archived variants are never returned. Variants are ordered oldest first: `created_at ASC`, then `catalogue_item_variant_id ASC` (UUIDv7) as a tiebreaker, because variants inserted together share one `created_at`. `None` when the item is missing, archived, or in another organization. An active item with no enabled variants also gives `None`, because the `INNER JOIN` matches nothing; the write paths already prevent that state. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositorySpec` covers the success case (exact oldest-first order with variants inserted out of order; archived and sibling-item variants excluded), each `None` case, and the only-archived-variants case.
- Testing-only `CatalogueQueries.getAllCatalogueItemWithVariantsRowsTesting` reads complete item and variant rows across every organization and lifecycle status without adding a repository or service API. It reuses the joined item/variant projection, joins on both `organization_id` and `catalogue_item_id`, groups by both ownership IDs so equal item IDs in different organizations stay separate, and orders each item's variants by `created_at ASC`, then `catalogue_item_variant_id ASC`. The item-list order is not a business contract. Its `INNER JOIN` intentionally omits a parent that has no variants because `CatalogueItemWithVariantsRow` requires a `NonEmptyChunk`.
- `getAllCatalogueItemSummariesEnabled(organizationID)` → `List[CatalogueItemSummaryRow]` (`catalogueItemID`, `name`, `imageAsset`, `status`, plus a `NonEmptyChunk` of `CatalogueItemVariantSummaryRow`: `catalogueItemVariantID`, `sku`, `label`, `price`, `sellingUnit`, `status`): one SQL statement, item `INNER JOIN` variant on `(organization_id, catalogue_item_id)`, selecting only the alias-qualified columns those two summary rows need (no `organization_id`, item `description`, variant `description`/`attributes`, or timestamps). Only items in `CatalogueItemStatus.enabled` and variants in `CatalogueItemVariantStatus.enabled` are returned, so disabled items and disabled variants never appear; there is no paging or filtering. Order is contractual: items oldest first (`i.created_at ASC`, then `i.catalogue_item_id ASC`), and each item's variants oldest first (`v.created_at ASC`, then `v.catalogue_item_variant_id ASC`), because batch-inserted rows share one `created_at`. `created_at` orders rather than name or ID alone, since PostgreSQL's collation and byte-wise UUID comparison do not match Scala's ordering, so tests could not state the expected order. The joined rows are grouped by `catalogueItemID` in Scala, keeping SQL order. An enabled item with no enabled variants matches nothing in the `INNER JOIN` and is left out; the write paths already prevent that state. The repository returns raw enabled variant rows, and `CatalogueItemSummaryGet` returns them as variant summaries; no from-prices or variant count is computed. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositorySpec` covers the success case (exact item and variant order with rows inserted out of order; disabled variants, a disabled item, and another organization's item excluded), the empty organization, the only-disabled-items case, and an enabled item with only disabled variants being left out.
- `getCatalogueItemSummariesEnabled(organizationID, catalogueItemIDs: NonEmptyChunk[CatalogueItemID])` → `List[CatalogueItemSummaryRow]`: the same query as `getAllCatalogueItemSummariesEnabled` (shared private helper in `CatalogueQueries`, same join, columns, enabled filters, contractual created-first ordering, and Scala grouping) plus `i.catalogue_item_id IN (...)`. Request order and duplicates in `catalogueItemIDs` do not affect the result; it follows the item `created_at` order. Requested IDs that match no enabled item with at least one enabled variant (missing, disabled, in another organization, or with only disabled variants) are simply absent, never an error. Errors map to `InternalServerError.RepositoryError`. `CatalogueRepositorySpec` covers the success case (exact order with IDs requested in reverse and rows inserted out of order; disabled variants and an unrequested enabled item excluded), a requested disabled item, requested missing and other-organization IDs, a requested item with only disabled variants, and no requested ID matching.
- Reads provide `getCatalogueItemWithVariantsActive` and the all/selected enabled-summary queries described above.
- Unique mapping adds `uq_catalogue_item_variant_sku` → 409.

## Image upload

`POST /upload/catalogue-item/image` is a Tapir streaming endpoint, not Smithy — Smithy JSON routes cap at 5 MB (`HttpApp.SmithyMaxEntitySize`); Tapir streams binary and allows 20 MB (`HttpApp.TapirMaxEntitySize`, kept equal to `file-service.file-bytes-max`). See [Alternate HTTP](../project/alternate-http.md) for the shared Tapir transport mechanics (docs mounting, error model, security wiring) this endpoint follows alongside [Organization Management](organization-management.md#logo-upload)'s logo upload — the two mirror the same pipeline shape, differing only in entity scoping and persistence target.

Binary body; organization in `X-Organization-ID`, catalogue item in `X-Catalogue-Item-ID`, original file name in `X-File-Name`. Security (`AuthorizationService.auth`): valid access JWT, `OnboardStage.completedStages` (= `PhoneVerified`), and the caller must be assigned to the organization as `Owner` or `Admin` (disallowed role → `403`, no membership row → `500`).

Errors: `TapirServerError` has no validation variant, so every 400 here is `BAD_REQUEST_ERROR` (never `VALIDATION_ERROR`). `HttpErrorHandler.errorResponseHandlerTapir` maps every `ServiceError.BadRequestError` — including `FileScanner`'s `ValidationError` for a missing/unsupported extension or an extension/detected-content mismatch — to `TapirServerError.BadRequestError`; a missing or undecodable `X-Organization-ID`/`X-Catalogue-Item-ID`/`X-File-Name` header goes through `tapir.scala`'s decode-failure handler, also `400 BAD_REQUEST_ERROR`. Missing/archived/foreign item, image decode/processing failure, and over-cap bytes are `500 INTERNAL_SERVER_ERROR`.

`FileService.uploadCatalogueItemImage` runs inside one `ZIO.scoped` block; every intermediate file is a `TempFile.createScoped` (auto-deleted on scope close, even on failure):

1. Load the active catalogue item through `CatalogueRepository.getCatalogueItemWithVariantsActive`; the repository returns `None` for a missing, archived, foreign-organization, or no-enabled-variant item, so the service fails with the stable missing-item `UnexpectedError` before any bytes are read.
2. `FileScanner.scan` validates the existing declared filename header, spools the incoming `ZStream[Byte]` to a temp file, and drains the entire input even past the byte cap (writing at most `fileBytesMax + 1` bytes, discarding the rest) so an oversized request body isn't abandoned mid-read (rationale: [Streaming uploads](../project/streaming-uploads.md)). It detects the actual MIME type with Apache Tika using the filename as a hint, requires the extension and detected MIME to agree, and rejects anything outside `SupportedMediaType.images` (`PNG`, `JPEG`, `WEBP`).
3. `ImageProcessing.normalize` re-detects the format with scrimage's `FormatDetector`, decodes, bounds to 640×640 px (`MaxDimensionPixels`), and re-encodes as lossless WebP. Yields the untouched original stream and the normalized variant.
4. `S3ClientOrganizationMedia.uploadImage` stores both variants at `{catalogueItemImageBucketPathPrefix}/{organizationID}/{catalogueItemID}/{originalFileName|normalizedFileName}` in bucket `organization-media`, returning both bucket keys as an `UploadedImageResult` (`imageOriginalS3BucketKey`/`imageNormalizedS3BucketKey`), from which the service builds a `CatalogueItemImageAsset` (composite `ImageAsset` newtype: original bucket key, normalized bucket key, original file name). `genMediaUrl` takes a single `S3BucketKey` and returns a presigned GET URL (`urlExpiresAtOffset`) as `S3MediaUrl`, shared for both original and normalized variants and across every kind of organization-owned media the client serves — catalogue-item images and (see [Organization Management](organization-management.md#logo-upload)) organization logos alike; images are never served through the gateway. `readiness` does a `HeadBucket` check for the health endpoint.
5. `CatalogueRepository.updateCatalogueItem` persists the `CatalogueItemImageAsset` with `nameOptUpdate` and `descriptionOptUpdate` unset and both variant input lists empty. `CatalogueItemStatus` is untouched — unlike the logo upload, this endpoint never transitions the owning row's lifecycle state.
