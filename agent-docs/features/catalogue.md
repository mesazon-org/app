## Schema

Edited in place in `V2025.05.27__init.sql`; no new migration, no data migration. Dev Flyway runs `clean, migrate`.

`catalogue_item`: PK `(organization_id, catalogue_item_id)`; `name text not null`, optional `description`, jointly optional image metadata, `status catalogue_item_status not null` (`Active`, `Inactive`), `is_archived boolean not null`, and required `created_at`/`updated_at` timestamps. `uq_catalogue_item_name` is partial unique `(organization_id, name) where is_archived = false`; archiving frees the name. The parent has no unit or price columns. Image metadata is the jointly optional original key, normalized key, and original filename, represented by `CatalogueItemImageAsset` over `ImageAsset`. All access is organization-scoped.

`catalogue_item_variant`:

- `organization_id uuid`, `catalogue_item_variant_id uuid`, `catalogue_item_id uuid`, PK `(organization_id, catalogue_item_variant_id)` so a variant can be found by ID alone (needed to detect "belongs to another item").
- FK `(organization_id, catalogue_item_id)` → `catalogue_item` `on delete restrict`; `idx_catalogue_item_variant_item` on `(organization_id, catalogue_item_id)`.
- `sku`, `label`, `description` nullable `text`; `attributes jsonb not null` (JSON object, name → value).
- `price_amount numeric` and `price_currency text` are jointly optional, enforced by `chk_catalogue_item_variant_price`.
- `selling_unit jsonb not null` stores the quantity, optional per-unit part, and optional unit-size part. The domain and validator enforce their value and unit rules.
- `status catalogue_item_variant_status not null`: native PG enum (`Active`, `Inactive`, `OutOfStock`), the same documented exception as `catalogue_item_status`; qualified casts as for the item.
- `is_archived boolean not null`, supplied explicitly on insert and preserved by general updates.
- `created_at`, `updated_at timestamptz not null`.
- `uq_catalogue_item_variant_sku`: partial unique `(organization_id, sku) where is_archived = false and sku is not null`; case-sensitive; mapped to 409, including duplicates within one request.
- Config: `RepositoryConfig.catalogueItemVariantTable` + `allTableNames` and both `application.conf` files are updated.

## Domain

- Enums: `CatalogueItemVariantStatus` (`Active`, `Inactive`, `OutOfStock`); `CatalogueItemStatus` (`Active`, `Inactive`). Neither enum classifies cases as enabled or disabled; archive state is a separate persisted Boolean. `CatalogueItemVariantUnit` is a sealed trait over three enums: `UnitSize` (`Gram`, `Kilogram`, `Millilitre`, `Litre`, `Millimetre`, `Centimetre`, `Metre`, `SquareMetre`), `PackageUnit` (`Pack`, `Box`), `PerUnit` (`Bag`, `Bottle`, `Can`, `Jar`, `Piece`).

The shared arbitrary reuses `arbCurrency`; Smithy transformations derive mirrored enums directly, and persistence reuses the generic enum-as-text codecs for `price_currency`. Owner wrapper `CatalogueItemVariantPrice` (`Pure[Price]`), optional on a variant.
- Selling unit (required on every variant): `CatalogueItemVariantSaleUnit(quantity: CatalogueItemVariantQuantity, perUnit: Option[CatalogueItemVariantPerUnit], unitSize: Option[CatalogueItemVariantUnitSize])`. `CatalogueItemVariantQuantity(value, unit: CatalogueItemVariantUnit)` takes any unit; `CatalogueItemVariantPerUnit(value, unit: CatalogueItemVariantUnit.PerUnit)` and `CatalogueItemVariantUnitSize(value, unit: CatalogueItemVariantUnit.UnitSize)` are restricted. The three value newtypes are `BigDecimal` refined `Positive & LessEqual[99999]`.
- Newtypes (Catalogue group): `CatalogueItemDescription`, `CatalogueItemVariantID`, `CatalogueItemVariantSku`, `CatalogueItemVariantLabel`, `CatalogueItemVariantDescription`, `CatalogueItemVariantAttributeName`, `CatalogueItemVariantAttributeValue` (text ones `NonEmptyTrimmed`), `CatalogueItemVariantQuantityValue`, `CatalogueItemVariantPerUnitValue`, `CatalogueItemVariantUnitSizeValue`.
- Attributes: free-form `Map[CatalogueItemVariantAttributeName, CatalogueItemVariantAttributeValue]`, no fixed vocabulary. Duplicate JSON keys are resolved last-wins by the decoder, so names are unique by type; duplicates in the raw body are not rejected.
- Update: the wire carries two lists, mirroring `CatalogueRepository.updateCatalogueItem`: `variantsUpdate` changes existing variants (each names its `catalogueItemVariantID`) and maps to `UpdateCatalogueItemVariantInput`; `variantsInsert` adds variants (full payload, no ID, no status: always stored `Active`, as on create) and maps to `InsertCatalogueItemVariantInput`. The response stays empty; a client needing the new variant IDs re-reads `GET /catalogue/item/{catalogueItemID}`. Clearable fields (item description; variant SKU, label, description, price) are `Option[Option[X]]`: outer `None` keeps, `Some(None)` clears. Attributes, selling unit, and status are plain `Option[X]`: replaced whole, never cleared.

## Validation

- Request types live in `Catalogue.scala`; `CatalogueRequestValidator` validates single insert, batch insert, item update, and name/SKU uniqueness. Archive and ID-only reads need no request validator. Shared `PriceValidator` validates `Price`, then the feature validator wraps it in `CatalogueItemVariantPrice`.
- Prices accept only exact uppercase Smithy currency codes `EUR`, `USD`, and `GBP`, without trimming or case conversion. `Currency.decimalPoints: Option[Int]` is `Some(2)` for these cases: reject supplied scales above two and append zeros to exactly two stored places, without rounding. A future `None` case has no scale restriction and preserves the amount. Amounts remain non-negative with at most 12 integer digits. For non-zero amounts, compare widened `precision - scale` before normalization to avoid allocating a compact extreme exponent; zero bypasses that representation-derived bound.
- Quantity, per-unit, and unit-size values are each greater than 0 and at most 99,999; validation preserves their supplied decimal places without rounding or a separate scale cap. Extremely precise values can pass validation yet exceed PostgreSQL `jsonb`'s numeric range when persisted; this is a known storage risk accepted for this rule.
- `CatalogueRequestValidator` validates selling-unit quantity, per-unit, and unit-size values directly, mapping their closed Smithy enums through Chimney and accumulating invalid numbers in field order. Its spec covers all unit cases, optional parts, exact decimal preservation, boundaries, and ordered errors. Variant prices delegate to `PriceValidator`.
- Insert item: at least one variant. The validated `CatalogueItemPostRequest.variants` is a `NonEmptyChunk`, built by shared `validateNonEmptyNested`; an empty input reports `InvalidFieldError("variant", "At least one variant must be provided", Seq.empty)`. Update `variantsInsert` entries: selling unit required (Smithy `@required`); price optional, as on insert (absent = no set price). Item and variant status updates accept every case in their respective closed enums; they do not alter archive state.
- Batch insert: at least one catalogue item. `CatalogueItemBatchPostRequest.catalogueItems` is a `NonEmptyChunk`, built by `validateNonEmptyNested("catalogueItem", ...)`; empty or omitted wire lists produce `InvalidFieldError("catalogueItem", "At least one catalogueItem must be provided", Seq.empty)`. Non-empty input retains item order and accumulated nested item/variant errors. Domain and Smithy arbitraries follow the same non-empty invariant.
- Error naming: indexed variant errors and the empty-variant error both use `variant`; batch nests under `catalogueItem`. Each error names the item index, then the variant index, then the field.
- Uniqueness: when both optional query fields are absent, return two ordered `InvalidFieldError`s, one for `name` and one for `sku`, each with an empty submitted-value list and the at-least-one-required message. Supplied invalid values retain their own field errors.
- The three unit fields and `currency` are closed Smithy enums on the wire, so an unknown unit or currency is a decode-time 400 that names neither the item nor the variant. Item and variant `status` updates use their two-case and three-case Smithy enums respectively. The removed `Archived` value is a decode-time 400, not a validator error.
- `PriceValidatorSpec` proves typed currency, monetary boundaries, and exact scale. `CatalogueRequestValidatorSpec` proves each fallible request's round-trip and ordered error accumulation, including variant and batch indexes. The shared `Price` arbitrary generates valid EUR, USD, and GBP prices; `CatalogueItemVariantPrice` reuses it.
- Domain validation errors preserve nested item/variant indexes and messages. The current HTTP error handler exposes only their ordered `fieldName` strings in `ValidationError.fields`; detailed nesting is not a claim about the HTTP payload.

## Service implementation

Use the existing `.local` / `.observed` / `.live` pattern with `CatalogueRequestValidator`, `CatalogueRepository`, and `S3ClientOrganizationMedia`. The generated organization header is converted to `OrganizationID` on every repository call. Request-to-input and row-to-response mappings use Chimney, with inline customization for inserted variant status, differently named nested row fields, and presigned URLs. No transaction or lifecycle rules move into the service.

| Operation | Service behavior and functional proof |
|---|---|
| `catalogueItemPost` | Validate before repository access; every inserted variant gets `Active`; return the created item ID; validation touches no repository; repository failures propagate unchanged. |
| `catalogueItemBatchPost` | Validate the whole batch first, rejecting an empty batch before repository access; validated items are a `NonEmptyChunk` passed in one repository call; preserve returned ID order; invalid entries prevent all writes; repository failures propagate unchanged. |
| `catalogueItemPut` | Preserve absent/set/clear semantics, forward optional item status, and map both variant lists; inserted variants get `Active`; pass no image update; invalid requests prevent repository access; repository failures propagate unchanged. Missing-item no-ops and invalid referenced variants remain repository-owned. |
| `catalogueItemArchivePut` | Forward organization/item IDs once and return no content; preserve repository success/no-op and failures unchanged. |

## Repository and transactions

- `CatalogueQueries` contains the item and variant queries; `CatalogueRepositorySpec` exercises them against PostgreSQL. Persisted item/variant rows and internal summary projections contain `isArchived`; public response shapes do not.
- Insert (single and batch): item plus its variants in one transaction, all-or-nothing. Public creation sets item and variant status to `Active` and both archive flags to `false`. Internal variant insert inputs retain their explicit status.
- `updateCatalogueItem(organizationID, catalogueItemID, nameOptUpdate, descriptionOptUpdate, imageAssetOptUpdate, statusOptUpdate, updateCatalogueItemVariantInputs, insertCatalogueItemVariantInputs)` is the single item update. Image upload sets only `imageAssetOptUpdate`; status is `None` and both variant lists are empty. The item `UPDATE` filters `is_archived = false` and implicitly locks the parent. Zero affected rows (missing, archived, or foreign organization) means silent no-op success, even with bogus variant IDs. Referenced variants must belong to this item and be non-archived. A count mismatch fails with one `InternalServerError.UnexpectedError` naming the item ID, requested variant IDs, and found rows, rolling back the parent update. Missing, foreign-parent, and archived variants are not distinguished. General item and variant updates never write archive flags, including bulk variant updates supplied with full persisted Rows.
- `archiveCatalogueItem`: one transaction. The parent update filtered by `is_archived = false` sets only its archive flag and `updatedAt`, preserving status and acquiring the same parent lock as general updates. Missing, already-archived, and foreign-organization parents are silent no-ops. Otherwise every non-archived child gets `isArchived = true` and the same timestamp; already-archived children retain their timestamps. Business statuses and retained fields/images are unchanged. Errors map to `InternalServerError.RepositoryError`. Concurrent archive and variant insertion cannot leave a non-archived child under an archived parent.
- `archiveCatalogueItemVariant`: one transaction. First lock the non-archived parent using `SELECT ... FOR NO KEY UPDATE`, without changing its timestamp. Missing, archived, or foreign parent is a silent no-op. Read the parent's non-archived variant IDs under that lock. Missing, foreign-parent, or already-archived target is a silent no-op. The sole remaining variant fails with `ForbiddenError.InvalidAction("archiveCatalogueItemVariant", ...)` (403); callers must archive the parent instead. Otherwise set only the target's archive flag and timestamp, preserving its business status. Every variant business status counts toward this guard. Other errors map to `InternalServerError.RepositoryError`. Of two concurrent attempts to archive the last two variants, exactly one succeeds and the other receives `InvalidAction`.
- Every variant-mutating transaction locks the parent first. This preserves at least one non-archived variant for a non-archived parent and prevents insertion/update races with parent archive.
- `getCatalogueItemWithVariants(organizationID, catalogueItemID)` returns `Option[CatalogueItemWithVariantsRow]` (parent plus a `NonEmptyChunk` of variants). One SQL `INNER JOIN` uses both ownership IDs and explicitly listed, alias-qualified columns, including internal archive flags. Variant ownership IDs come from the parent projection. Both sides filter `is_archived = false`, independently of business status. Variants order by `created_at ASC`, then `catalogue_item_variant_id ASC`. Missing, archived, foreign-organization, or no-non-archived-variant parents return `None`; normal writes prevent the last state. Errors map to `InternalServerError.RepositoryError`.
- Testing-only `CatalogueQueries.getAllCatalogueItemWithVariantsRowsTesting` reads complete rows across every organization, business status, and archive flag. It reuses the joined projection, joins/groups by both ownership IDs, and orders variants by creation time then ID. Item-list order is not contractual. Its `INNER JOIN` omits parents with no variants because the container requires `NonEmptyChunk`. It adds no repository/service API and has no dedicated tests.
- `getAllCatalogueItemSummaries(organizationID)` returns `List[CatalogueItemSummaryRow]`: item ID, name, image asset, status, internal archive flag, and non-empty variant summaries (ID, SKU, label, price, selling unit, status, internal archive flag). One joined query selects only projection columns, omitting organization ID, descriptions, attributes, and timestamps. Both tables filter only on archive state. Order is contractual: items by `i.created_at ASC`, then item ID; variants by `v.created_at ASC`, then variant ID. Creation time avoids relying on differences between PostgreSQL and Scala name/UUID ordering. Scala grouping preserves SQL order. Parents with no non-archived variant are absent. Service responses omit internal archive flags and resolve image assets to presigned URLs; there is no price aggregation or variant count. Errors map to `InternalServerError.RepositoryError`.
- `getCatalogueItemSummaries(organizationID, catalogueItemIDs: NonEmptyChunk[CatalogueItemID])` shares the summary query and grouping, adding `i.catalogue_item_id IN (...)`. Request order and duplicates do not affect output order. Missing, archived, foreign-organization, and no-non-archived-variant IDs are silently absent. Errors map to `InternalServerError.RepositoryError`.
- Name and case-sensitive SKU uniqueness use the same non-archived predicates as their partial indexes. `Inactive` items reserve names, and every non-archived variant status reserves its SKU. Stable constraints map to 409, including `uq_catalogue_item_variant_sku`.

## Image upload

`POST /upload/catalogue-item/image` is a Tapir streaming endpoint, not Smithy — Smithy JSON routes cap at 5 MB (`HttpApp.SmithyMaxEntitySize`); Tapir streams binary and allows 20 MB (`HttpApp.TapirMaxEntitySize`, kept equal to `file-service.file-bytes-max`). See [Alternate HTTP](../project/alternate-http.md) for the shared Tapir transport mechanics (docs mounting, error model, security wiring) this endpoint follows alongside [Organization Management](organization-management.md#logo-upload)'s logo upload — the two mirror the same pipeline shape, differing only in entity scoping and persistence target.

Binary body; organization in `X-Organization-ID`, catalogue item in `X-Catalogue-Item-ID`, original file name in `X-File-Name`. Security (`AuthorizationService.auth`): valid access JWT, `OnboardStage.completedStages` (= `PhoneVerified`), and the caller must be assigned to the organization as `Owner` or `Admin` (disallowed role → `403`, no membership row → `500`).

Errors: `TapirServerError` has no validation variant, so every 400 here is `BAD_REQUEST_ERROR` (never `VALIDATION_ERROR`). `HttpErrorHandler.errorResponseHandlerTapir` maps every `ServiceError.BadRequestError` — including `FileScanner`'s `ValidationError` for a missing/unsupported extension or an extension/detected-content mismatch — to `TapirServerError.BadRequestError`; a missing or undecodable `X-Organization-ID`/`X-Catalogue-Item-ID`/`X-File-Name` header goes through `tapir.scala`'s decode-failure handler, also `400 BAD_REQUEST_ERROR`. Missing/archived/foreign item, image decode/processing failure, and over-cap bytes are `500 INTERNAL_SERVER_ERROR`.

`FileService.uploadCatalogueItemImage` runs inside one `ZIO.scoped` block; every intermediate file is a `TempFile.createScoped` (auto-deleted on scope close, even on failure):

1. Load the non-archived catalogue item through `CatalogueRepository.getCatalogueItemWithVariants`; the repository returns `None` for a missing, archived, foreign-organization, or no-non-archived-variant item, so the service fails with the stable missing-item `UnexpectedError` before any bytes are read.
2. `FileScanner.scan` validates the existing declared filename header, spools the incoming `ZStream[Byte]` to a temp file, and drains the entire input even past the byte cap (writing at most `fileBytesMax + 1` bytes, discarding the rest) so an oversized request body isn't abandoned mid-read (rationale: [Streaming uploads](../project/streaming-uploads.md)). It detects the actual MIME type with Apache Tika using the filename as a hint, requires the extension and detected MIME to agree, and rejects anything outside `SupportedMediaType.images` (`PNG`, `JPEG`, `WEBP`).
3. `ImageProcessing.normalize` re-detects the format with scrimage's `FormatDetector`, decodes, bounds to 640×640 px (`MaxDimensionPixels`), and re-encodes as lossless WebP. Yields the untouched original stream and the normalized variant.
4. `S3ClientOrganizationMedia.uploadImage` stores both variants at `{catalogueItemImageBucketPathPrefix}/{organizationID}/{catalogueItemID}/{originalFileName|normalizedFileName}` in bucket `organization-media`, returning both bucket keys as an `UploadedImageResult` (`imageOriginalS3BucketKey`/`imageNormalizedS3BucketKey`), from which the service builds a `CatalogueItemImageAsset` (composite `ImageAsset` newtype: original bucket key, normalized bucket key, original file name). `genMediaUrl` takes a single `S3BucketKey` and returns a presigned GET URL (`urlExpiresAtOffset`) as `S3MediaUrl`, shared for both original and normalized variants and across every kind of organization-owned media the client serves — catalogue-item images and (see [Organization Management](organization-management.md#logo-upload)) organization logos alike; images are never served through the gateway. `readiness` does a `HeadBucket` check for the health endpoint.
5. `CatalogueRepository.updateCatalogueItem` persists the `CatalogueItemImageAsset` with `nameOptUpdate`, `descriptionOptUpdate`, and `statusOptUpdate` unset and both variant input lists empty. Business status and archive flags are preserved. Non-archived `Inactive` items are eligible for the same upload pipeline.
