# Catalogue

Organization-scoped items with variants, exact prices, selling units, and item images. Product contract: [Catalogue epic](../../pages/epics/06-catalogue.md).

## Status and scope

| Slice | Current implementation | Remaining |
|---|---|---|
| Endpoints | Eight canonical Smithy operations and both mounted Catalogue file routes, with security/message validation and a shared OpenAPI docs route | Both catalogue file routes have HTTP verification; JSON decimal precision is an accepted limitation |
| Validation | Typed currency, nested validation, non-empty creates, nullable updates | Storage limits and duplicate update IDs are documented below |
| Schema | Item and variant tables in the pre-release init migration | No conversion for an already deployed database |
| Repository | Tenant-scoped reads/writes, transactions, archive locks, uniqueness indexes | Known edge cases below |
| Service | Validation, mappings, image signing, upload integration | Coverage boundaries below; not a release/deployment claim |
| File extraction | Image/PDF/CSV/XLS/XLSX previews through `CatalogueFileService.aiExtract`, strict AI schemas, separate AI/public models, computed notes/attention, upload-wide spreadsheet duplicates, and endpoint-specific byte limits; HTTP and functional coverage below. Since issue 607: structured `FieldInfo` reporting, service-computed duplicates for every source, kept unit-less variants and currency-less prices, nameless candidates, notes compaction, processing-message priority | PDF live golden verification is pending, user-run ([PDF extraction](#pdf-extraction)); AI metadata validation is explicitly deferred; cross-batch grouping is deferred (follow-up 13); no extraction persistence |

Orders, paging/search, unarchive, and variant-specific images are outside this feature. The canonical implementation uses `CatalogueService`, `CatalogueRequestValidator`, `CatalogueRepository`, and `CatalogueQueries`; there is no parallel versioned service.

Business status and archiving are independent. Items have `Active`/`Inactive`; variants have `Active`/`Inactive`/`OutOfStock`. **Every business status is usable while `isArchived = false`.** The archive flag alone controls visibility, updates, uploads, name/SKU reservation, and last-variant counting. Do not reintroduce enabled/disabled status lists or duplicate ordinary test cases per status. Creation starts items and variants `Active` and non-archived; only dedicated archive operations can set the archive flag.

## Endpoints

`CatalogueService.smithy` and `domain/Catalogue.smithy` use namespace `io.mesazon.gateway.smithy`. The service requires `@simpleRestJson`, bearer authentication, and completed onboarding. Every operation mixes `OrganizationScopedInput` (`X-Organization-ID`). Mutations allow Owner/Admin; reads allow Owner/Admin/User. `Main` supplies the layers and `HttpApp` mounts the service and Swagger with the shared middleware.

| Operation | Method / URI | Success | Additional errors beyond BadRequest, Unauthorized, Forbidden, InternalServerError |
|---|---|---|---|
| `CatalogueItemPost` | `POST /catalogue/item` | 200, item ID | ValidationError, Conflict |
| `CatalogueItemBatchPost` | `POST /catalogue/item/batch` | 200, item IDs in input order | ValidationError, Conflict |
| `CatalogueItemPut` | `PUT /catalogue/item/{catalogueItemID}` | 204 | ValidationError, Conflict |
| `CatalogueItemArchivePut` | `PUT /catalogue/item/{catalogueItemID}/archive` | 204 | — |
| `CatalogueItemVariantArchivePut` | `PUT /catalogue/item/{catalogueItemID}/variant/{catalogueItemVariantID}/archive` | 204 | Forbidden includes the last-variant rule |
| `CatalogueItemGet` | `GET /catalogue/item/{catalogueItemID}` | 200, full item and variants | — |
| `CatalogueItemSummaryGet` | `GET /catalogue/item/summary` | 200, item and variant summaries | — |
| `CatalogueItemUniquenessGet` | `GET /catalogue/item/uniqueness` | 200, optional uniqueness booleans | ValidationError |

IDs of addressed resources are path labels, never repeated in the body. Archive requests have no body. Static `/summary` and `/uniqueness` paths take precedence over the item-ID route. See [Smithy conventions](../standards/smithy.md) and [authentication](../project/authentication.md) for shared routing/auth rules.

- **Create:** `CatalogueItemPostRequest{name, description?, variants}`; each `CatalogueItemVariantInsert` has optional SKU, label, description and price, default-empty attributes, and required selling unit. No status/archive input. Batch `catalogueItems` reuses the single-create request. Wire lists default to empty; validation requires at least one item/variant.
- **Update:** optional name, nullable description, optional item status, and default-empty `variantsUpdate`/`variantsInsert`. Existing-variant entries require `catalogueItemVariantID`; SKU, label, description and price are nullable, while attributes, selling unit and status are optional replacements. Insert entries reuse the create shape and default to `Active`. A 204 response contains no newly inserted variant IDs; re-read detail to obtain them.
- **Detail:** item ID, name, optional description, status, optional `imageNormalizedUrl`, and variants. Each full variant contains its ID, optional SKU/label/description/price, required attributes/selling unit/status. Internal ownership, archive flags, and audit timestamps are omitted.
- **Summary:** optional repeated `catalogueItemIDs` query key; absent or empty list selects all non-archived items. Response `catalogueItemSummaries` contains item ID/name/status/optional image URL and required variant summaries (ID, optional SKU/label/price, selling unit, status). No descriptions, attributes, archive flags, price aggregation, or variant count. Unknown/archived/foreign IDs are omitted. Duplicate IDs and request order do not affect the result.
- **Uniqueness:** optional `name`/`sku`, at least one required. Only supplied fields produce `isNameUnique`/`isSkuUnique`. Names compare case-sensitively; SKUs compare case-insensitively. The check reserves nothing; a subsequent write may still conflict.

Value shapes for price and selling units are shared by requests/responses; operation-specific entity views remain distinct. Request lists use `@default([])`; response lists/maps are required. The combined Smithy quantity-unit enum flattens the domain unit groups; narrow per-unit and unit-size enums retain their restrictions.

## Validation

`CatalogueRequestValidator` exposes validated single-create, batch-create, update, and uniqueness methods. Archive and ID-only reads need no request validator. Errors accumulate in field/input order before repository access.

| Input | Rule |
|---|---|
| Item name/description; variant SKU/label/description; attribute names/values | 1–255 characters, trimmed and non-empty; reject rather than normalize |
| `Price.currency` | Domain `Currency` enum, mirrored by closed Smithy `Currency`: exact uppercase EUR/USD/GBP |
| `Price.amount` | Non-negative, at most 12 integer digits; currency-specific decimal rule below |
| Quantity, per-unit, unit-size values | `0 < value <= 99999`; preserve every supplied decimal place, no rounding or scale cap |
| Quantity unit | Gram, Kilogram, Millilitre, Litre, Millimetre, Centimetre, Metre, SquareMetre, Pack, Box, Bag, Bottle, Can, Jar, Piece |
| Per-unit unit | Bag, Bottle, Can, Jar, Piece |
| Unit-size unit | Gram, Kilogram, Millilitre, Litre, Millimetre, Centimetre, Metre, SquareMetre |
| Attributes | Free-form map; no vocabulary/count limit. Map decoding does not reject repeated raw JSON keys; the HTTP decoder has a separate collection limit below |
| Create/batch collections | Non-empty; no validator count cap. HTTP decoding applies the collection limit below |

Shared `PriceValidator` returns `Price(amount: PriceAmount, currency: Currency)`; the request validator wraps it in `CatalogueItemVariantPrice` (`Pure[Price]`). `Currency.decimalPoints: Option[Int]` is `Some(2)` for all current currencies. Reject supplied scale above two, including trailing zeroes (`1.230`); pad smaller scales to exactly two without rounding. Future `None` means unrestricted scale and preservation of the supplied amount. For non-zero amounts, widened `precision - scale` is checked before normalization to reject compact huge exponents without expanding them; zero bypasses that representation-derived bound. Price is stored as exact decimal, never floating point.

The feature validator owns selling-unit validation. It maps closed unit/status enums through Chimney and accumulates invalid quantity/per-unit/unit-size errors. Unknown enum strings fail transport decoding (400), before request validation. All current business statuses are valid updates.

`validateNonEmptyNested(fieldName, ...)` delegates entry validation to `validateAllNested` and returns `NonEmptyChunk`. Pass singular `variant` for create variants and `catalogueItem` for batch items; an empty list produces `At least one <fieldName> must be provided`. Nested errors retain item index, variant index and field. Domain models and arbitraries preserve these non-empty invariants. The domain module depends on ZIO core for this collection.

When neither uniqueness parameter is supplied, return two ordered errors, `name` then `sku`, rather than one combined field. Invalid supplied values retain their own errors. HTTP `ValidationError.fields` exposes only ordered field names; nested indexes/messages are validator-level detail.

Nullable update fields use `Option[Option[T]]`: `None` keeps, `Some(None)` clears, `Some(Some(value))` replaces. Attributes/selling unit/status use `Option[T]`: absent keeps, present replaces whole; an empty attributes map clears it. Request validators preserve omission and explicit null rather than applying create defaults.

`backend/schemas/migrations/V2025.05.27__init.sql` is modified in place under the approved **pre-release** policy. This PR contains no deployed-data conversion. Do not run destructive clean/migrate against a database whose data must be retained. See [schema flow](flow/03-schema.md) and [PostgreSQL](../standards/postgres.md).

| Table | Stored columns / constraints |
|---|---|
| `catalogue_item` | Composite PK `(organization_id, catalogue_item_id)`; name, optional description, optional original/normalized image keys and original filename (one optional image asset in the domain), native-enum status, required `is_archived`, creation/update timestamps |
| `catalogue_item_variant` | Composite PK `(organization_id, catalogue_item_variant_id)`; parent item ID; optional SKU/label/description; required attributes JSONB; jointly optional numeric price amount/text currency; required selling-unit JSONB; native-enum status, required `is_archived`, creation/update timestamps |

- Composite variant FK `(organization_id, catalogue_item_id)` references the item with `on delete restrict`. `idx_catalogue_item_variant_item` supports parent lookup.
- `uq_catalogue_item_name`: unique `(organization_id, name)` where `is_archived = false`.
- `uq_catalogue_item_variant_sku`: unique `(organization_id, lower(sku))` where `is_archived = false and sku is not null`. Lookup uses the same PostgreSQL `lower` expression; stored spelling is preserved. Archive frees the name/SKU. Stable index names map conflicts to HTTP 409.
- `chk_catalogue_item_variant_price` requires amount and currency to be present or absent together. There is no corresponding all-or-none image-column CHECK; application writes construct the complete image asset. - `catalogue_item_status` and `catalogue_item_variant_status` are approved native-enum exceptions. Queries cast values to their schema-qualified enum on writes and to text on reads. Currency uses the shared enum-as-text codec.
- `CatalogueItemImageAsset` wraps `ImageAsset`; `CatalogueItemVariantPrice` wraps `Price`. Generic Iron/composite codecs preserve their positional field order. Explicit joined projections must remain aligned with `Read`/Row order.
- Attributes use shared refined-string JSON key codecs in `queries.scala`; direct validated-string encoding avoids recursive jsoniter derivation for opaque keys. Selling units use the domain JSON representation. Selling-unit values are decoded through the refined domain codecs, not the request validator. The selling-unit codec uses jsoniter's default decimal precision and read limits. The resulting rounding/read limitation is accepted for expected business values; see issue 12.
- `RepositoryConfig.catalogueItemTable`/`catalogueItemVariantTable`, `allTableNames`, and both main/acceptance `application.conf` files name the tables.

## Repository and transactions

`CatalogueQueries` owns both tables. `CatalogueRepository` supplies `TimeProvider`, `IDGenerator` and one transaction per operation. UUIDv7 IDs and audit times come from application services, not database defaults.

### Writes and archive

- Single create inserts parent and its non-empty variants atomically. Batch create inserts every item and variant in one transaction and returns item IDs in request order. Any failure rolls back the whole operation.
- Update first updates/locks the tenant's non-archived parent, including `updated_at`. A missing, archived, or foreign parent yields 204 with no child writes. An otherwise empty update still advances the parent's timestamp.
- Existing-variant IDs must resolve to non-archived variants of that parent/organization. A count mismatch fails with 500 and rolls back the parent and all child writes. The current check also rejects duplicate IDs in `variantsUpdate` this way.
- Existing-variant updates merge optional fields into the loaded full rows, then write them together; new variants are inserted in the same transaction. Uniqueness conflicts return 409 and roll back every change. General update SQL and input models cannot set `is_archived`.
- Item archive marks the non-archived parent and all its non-archived variants archived with the operation timestamp. Business values/statuses and creation times remain. Already archived children are not rewritten. Missing/foreign/already archived parents are no-ops. Images and records remain stored; no unarchive exists.
- Variant archive locks the non-archived parent with `FOR NO KEY UPDATE`, reads its non-archived variant IDs, and archives only the requested target. Missing/foreign/archived/wrong-parent targets are no-ops. Archiving the last non-archived variant fails with `ForbiddenError.InvalidAction` (403). Successful child archive does not change the parent/siblings. Parent locking serializes competing updates/archive operations so concurrent last-two-variant requests cannot archive both.

### Reads

- `getCatalogueItemWithVariants` uses one tenant-scoped `INNER JOIN`, filtering both archive flags. It returns `Option[CatalogueItemWithVariantsRow]`, whose children form a `NonEmptyChunk`. Children sort by creation time then variant ID. Missing/archived/foreign parents, and anomalous parents without a non-archived child, return `None`.
- `getAllCatalogueItemSummaries` and `getCatalogueItemSummaries(NonEmptyChunk[CatalogueItemID])` share one projection/grouping path. Items sort by creation time then item ID; variants by creation time then variant ID. Grouping retains SQL order. Parents without a non-archived child disappear. Summary Rows omit archive flags and unused descriptions/attributes.
- Name/SKU checks use the same tenant/archive predicates as their indexes, regardless of business status. They are advisory reads, not reservations.
- `getAllCatalogueItemWithVariantsRowsTesting` is a testing-only joined read across organizations/statuses/archive flags. It uses complete Rows and includes archived records; its inner join still omits parents with no variants. It is not a service/repository API and has no dedicated testing-query tests.

## Service and transformations

`CatalogueService.local` exposes typed `ServiceTask`; `.observed` maps errors through `HttpErrorHandler`; `.live` composes them. The service validates before repository calls, maps generated UUIDs to domain IDs, sets inserted variant status to `Active`, forwards archive operations, and maps full Rows/projections back to Smithy.

Detail maps a missing repository result to the existing 500 `UnexpectedError`. Detail/summary sign only present normalized image keys with `S3ClientOrganizationMedia.genMediaUrl`; absent images make no S3 call. Repository and signing failures propagate. Summaries preserve repository order and fail the request if any required signing call fails. Uniqueness checks only supplied fields, name before SKU, stopping on failure.

Shared Chimney givens live in `gateway/transform/transform.scala`: `NonEmptyChunk` to `List` and `Option` to Smithy `Nullable`. Import `io.mesazon.gateway.transform.given` for those and `io.github.iltotore.iron.chimney.given` for Iron refined product to target product; do not add per-price delegates or exports. Mirrored enums and unchanged nested price fields derive automatically. See [Chimney](../standards/chimney.md).

## Image upload

`POST /catalogue/file/upload/image/item` is the Catalogue file image-upload route. It uses Tapir streaming transport: binary body, `X-Organization-ID`, `X-Catalogue-Item-ID`, `X-File-Name`, and bearer token. Completed onboarding and Owner/Admin membership are required. Success is 200 with an empty body. See [alternate HTTP](../project/alternate-http.md), [streaming uploads](../project/streaming-uploads.md), and the shared [organization-logo pipeline](organization-management.md#logo-upload).

`CatalogueFileService.uploadImageItem` runs in `ZIO.scoped`:

1. Read through `getCatalogueItemWithVariants`; reject missing/archived/foreign/no-non-archived-child targets with 500 before scanning bytes or writing objects. Business status is irrelevant.
2. `FileScanner.scan` checks filename/extension, spools to a scoped temporary file, detects MIME using Tika, and requires extension/content agreement for PNG/JPEG/WEBP. It drains excess input while retaining at most the cap plus one byte; scoped files are deleted on success/failure.
3. `ImageProcessing.normalize` detects/decodes with scrimage, bounds dimensions to 640×640, and re-encodes lossless WebP. The original is retained unchanged.
4. `S3ClientOrganizationMedia.uploadImageCatalogueItem` uploads original then normalized bytes to fixed keys `{catalogueItemImageBucketPathPrefix}/{organizationID}/{catalogueItemID}/{originalFileName|normalizedFileName}`. Later uploads overwrite those keys.
5. Persist `CatalogueItemImageAsset` with the original filename and returned keys through `updateCatalogueItem`, leaving name/description/status unset and both child lists empty. S3 and PostgreSQL do not share a transaction; see issues below.

Defaults: Smithy JSON cap 5 MiB (`HttpApp.SmithyMaxEntitySize`), Tapir cap 20 MiB (`TapirMaxEntitySize`), scanner cap `file-service.file-bytes-max = 20971520`; keep upload caps aligned. S3 config uses bucket `organization-media`, catalogue prefix `catalogue/item-images`, filenames `original`/`normalized`, and `url-expires-at-offset = 15 minutes`. `genMediaUrl` returns presigned URLs; the gateway does not serve image bytes. `readiness` uses `HeadBucket`.

`CatalogueFileServiceConfig` declares separate 20 MiB scanner limits for image upload and catalogue extraction under `catalogue-file-service.upload-catalogue-item-image-file-bytes-max` and `catalogue-file-service.extract-catalogue-items-file-bytes-max`. Their optional environment overrides are `CATALOGUE_FILE_SERVICE_UPLOAD_CATALOGUE_ITEM_IMAGE_FILE_BYTES_MAX` and `CATALOGUE_FILE_SERVICE_EXTRACT_CATALOGUE_ITEMS_FILE_BYTES_MAX`. `CatalogueFileService` now depends on this config and passes `uploadCatalogueItemImageFileBytesMax` to the image scanner. Photo and spreadsheet extraction pass `extractCatalogueItemsFileBytesMax` to the scanner. The remaining organization-logo/customer-extraction `FileService` routes still consume `FileServiceConfig.fileBytesMax`; `Main` now registers `CatalogueFileService.live` and `CatalogueFileServiceConfig.live`; both catalogue routes are mounted and the legacy image route is removed. Functional tests use distinct image/extraction limits to prove selection of the image-specific field. The registered config layer reads these optional deployment overrides; the committed defaults remain 20 MiB.

Tapir errors have no validation variant: missing/malformed required headers, unsupported extensions and content/extension mismatch map to 400 `BAD_REQUEST_ERROR`. Missing/archived/foreign targets and processing failures map to 500; disallowed role to 403; missing membership currently to 500. Scanner over-cap failure is internal, but real HTTP may stall before a response (known issue below).

## Catalogue file extraction

Follow the [AI extraction standard](../standards/ai-extraction.md) for model/schema ownership, structured field reporting, user-facing note lists, instruction priority, aggregation, and verification. The following rules define Catalogue's specific contract.

`CatalogueFileService` owns the mounted `/catalogue/file/upload/image/item` and `/catalogue/file/ai/extract` routes and their separate OpenAPI spec, registered in Swagger. Image upload uses `catalogueFileUploadImageItemPostEndpoint` → `uploadImageItem`; extraction uses `catalogueFileAiExtractPostEndpoint` → `aiExtract`. The legacy `/upload/catalogue-item/image` route, its OpenAPI entry, client method, and 14 `FileApiSpec` cases are removed. The obsolete catalogue image method, observed wrapper, repository dependency, and functional tests have also been removed from `FileService`; it now owns only organization-logo upload and customer extraction. The new image route preserves authorization, scan/normalize/S3/database behavior, and success/error responses. No schema migration or new external dependency was added. Client review/submission handling remains outside this repository.

The new endpoint is a raw Tapir `streamBinaryBody` upload with required `X-File-Name`, optional single-line `X-Processing-Message`, and the existing `X-Organization-ID` plus bearer security inputs. It requires completed onboarding and Owner/Admin membership. The processing message is trimmed before validation; blank becomes absent, and over 2,000 characters produces `400 BAD_REQUEST_ERROR` using the existing shared `code`/`message` response body. Other malformed headers use the same error shape. No new validation-error case, `fields` payload, or shared error-registry refactor is needed. `FileScanner.scan` applies `SupportedMediaType.aiExtractData` (images, PDF and spreadsheets; see [PDF extraction](#pdf-extraction)) and the existing 20 MB disk-backed cap; the upload remains fully drained. Excel/CSV use `SpreadsheetTool` and only Excel's first sheet. No image processing, S3 upload, repository write, or saved extraction result occurs in this route.

`CatalogueFileServiceEndpoints.scala` now declares `POST /catalogue/file/ai/extract`: typed filename, optional raw processing-message header, octet-stream body, public preview response, existing 400/401/403/500 errors, and Owner/Admin plus completed-onboarding documentation. Its path-based endpoint name is `catalogueFileAiExtractPostEndpoint`; its handler calls the service operation `aiExtract`. The public response is `CatalogueFileAiExtractPostResponse`, following the Smithy path-segment and HTTP-method naming convention. It generates a separate `CatalogueFileService` OpenAPI document. The mounted route builder now enforces completed onboarding and Owner/Admin authorization, trims the processing message, treats blank guidance as absent, validates the refined message before invoking `aiExtract`, and maps invalid guidance to the existing `400 BAD_REQUEST_ERROR`. It exposes its OpenAPI document through an optional docs route. The same builder also declares `POST /catalogue/file/upload/image/item` with the existing typed headers, streamed body, authorization, empty 200 response, and 400/401/403/500 errors, delegating to `CatalogueFileService.uploadImageItem`. Both endpoints appear in the Catalogue file OpenAPI document. `HttpApp` combines both file-service route sets under the existing Tapir entity limiter, serves both docs routes before Swagger, and registers the Catalogue file spec in Swagger. The legacy image route is removed. `CatalogueFileApiSpec` verifies both new routes; current case counts and remaining boundaries are recorded below. The raw optional string lets the extraction handler trim and discard blanks before constructing `CatalogueFileProcessingMessage`.

### AI result

The AI types stay in `domain/gateway/Catalogue.scala`, are registered strictly in `json/ai.scala`, and are never returned to clients. Every value uses its strict domain type. Absence is `None` and is never mirrored by a `missing…` flag. The schema sent to OpenAI does not carry `NonEmptyTrimmed`, so the prompts state it: an absent value is `null`, never `""`. A value that breaks a strict type fails the whole read (accepted trade-off, as in Customer Book).

- `CatalogueFileAIExtract(entriesIdentified: Long, entriesProcessed: Long, candidates: List[CatalogueItemAIExtract], emptyEntryRows: List[Long], unidentifiedEntryRows: List[Long], extractionNotes: List[String])`. Field names are unchanged. Counts and rows stay AI-reported and are never validated (follow-up 14).
- `CatalogueItemAIExtract(name: Option[CatalogueItemName], description: Option[CatalogueItemDescription], variants: List[CatalogueItemVariantAIExtract], extractionNotes: List[String])`.
- `CatalogueItemVariantAIExtract(sku: Option[CatalogueItemVariantSku], label: Option[CatalogueItemVariantLabel], description: Option[CatalogueItemVariantDescription], attributes: List[CatalogueItemVariantAttributesAIExtract], price: Option[CatalogueItemVariantPriceAIExtract], sellingUnit: Option[CatalogueItemVariantSaleUnit], sellingUnitInferred: Boolean, extractionNotes: List[String])`.

| Flag | Meaning | Final owner |
|---|---|---|
| `sellingUnitInferred` | `true` when the selling unit was worked out from product wording, an explicit shared header or group, or the processing message, rather than read from the variant's own unit value. A bare unit implying a quantity of one, a routine unit translation and a common alias count as read | AI sets it and adds an AI note, except when the unit came from the processing message (no note). ### Public preview

- `CatalogueFileAiExtractPostResponse(candidates: List[CatalogueItemCandidate], infoNotes: List[String], extractionNotes: List[String])`. The shape is unchanged.
- `CatalogueItemCandidate(name: Option[CatalogueItemName], description: Option[CatalogueItemDescription], variants: List[CatalogueItemVariantCandidate], inferredFields: List[FieldInfo], missingFields: List[FieldInfo], duplicateFields: List[FieldInfo], needsAttention: Boolean, extractionNotes: List[String])`.
- `CatalogueItemVariantCandidate(sku, label, description, attributes: Map[CatalogueItemVariantAttributeName, CatalogueItemVariantAttributeValue], price: Option[CatalogueItemVariantPriceCandidate], sellingUnit: Option[CatalogueItemVariantSaleUnit])`.
- `CatalogueItemVariantPriceCandidate(amount: PriceAmount, currency: Option[Currency])`. It is a plain preview product, not a `Pure` newtype. Its amount is mandatory and only the currency may be absent, so it does not break the [Scala rule](../standards/scala.md) against parallel `Option`s for joint presence. The add flow still requires both and rejects the candidate until the user supplies the currency (`chk_catalogue_item_variant_price`).
- `CatalogueItemVariantInsert` is unchanged and remains the add-flow type only. No add validator runs in the preview.
- **Wire format.** The response codec is the default `JsonCodecMaker.make`, whose `transientEmpty` covers every `Iterable`, `Map` included, and whose `transientNone` covers `Option`. So empty lists, an empty `attributes` map and an absent name, selling unit, price or currency are omitted. `needsAttention` has no default and is always written. The acceptance client decodes with the same codec, so an omitted list or map decodes as empty. The Tapir schema for `attributes` is marked optional, because Tapir marks iterables optional but not maps. Without that, OpenAPI would show `attributes` as required.
- **Registrations.** `json/tapir.scala` registers the three new public types. The `CatalogueItemVariantInsert` and `Price` schemas and codecs there have no other user, so they are removed. `json/ai.scala` derives `CatalogueItemVariantPriceAIExtract` bottom-up and imports `currencySchema` instead of `priceSchema`.

`FieldInfo` paths. The vocabulary is closed, and the service writes only these:

| `path` | Listed in |
|---|---|
| `/name` | `missingFields` when `None`; `duplicateFields` when the name is a duplicate |
| `/variants` | `missingFields` when the variant list is empty |
| `/variants/{i}/sku` | `duplicateFields` when the SKU is a duplicate |
| `/variants/{i}/sellingUnit` | `missingFields` when `None`; otherwise `inferredFields` when `sellingUnitInferred` |
| `/variants/{i}/price/currency` | only when `price` is present: `missingFields` when `currency` is `None`; otherwise `inferredFields` when `currencyInferred` |

`i` is the 0-based position in the candidate's own variant list. The mapping drops no variant, so it is also the AI list position. A missing value is never also listed as inferred. Item paths come first, then each variant's paths in variant order, in the order of the table. The lists are never de-duplicated. Paths are built by the shared helper `FieldInfo.fromPathSegments` in the domain `FieldInfo` companion (already used by Customer Book), which escapes `~` and `/`. A missing `/name` or `/variants` points at a property the wire omits. The path-resolution test therefore checks the pointer against the Tapir schema and requires only the parent (the candidate object) to resolve, exactly as Customer Book's does.

### `CatalogueFileService.aiExtract`

1. `FileScanner.scan` with `extractCatalogueItemsFileBytesMax` and `SupportedMediaType.aiExtractData` (images, PDF and spreadsheets; shared with Customer Book). An image goes to `extractFromImage`, a PDF to `extractFromPdf`, a spreadsheet to `extractFromCsv`.
2. Images go to `extractFromImage[CatalogueFileAIExtract]` with the image instructions and the optional message. They are neither merged nor compacted.
3. Spreadsheets: `convertExcelToCsv` / `convertToCsv`, then `extractFromCsv[CatalogueFileAIExtract]` with the file instructions and the optional message. Then the merge and compaction step below. *Issue 607 rework (agreed, not built):* the step moves unchanged from `CatalogueFileServiceImpl` into the companion as `private[gateway] def mergeAndCompactCatalogueFileAIExtracts(aiClientDataExtraction, catalogueFileAIExtracts): UIO[CatalogueFileAIExtract]`, shared with the [manual golden check](#manual-ai-golden-checks). The pure `mergeCatalogueFileAIExtracts` only sums both counts and concatenates candidates, both row lists and top-level notes in group order. It no longer computes duplicates. With two or more groups and non-empty merged notes, `aiClientDataExtraction.noteCompaction(notes, AIInstructions.compactCatalogueFileNotesInstructions)` runs. Its output is accepted only when it is non-empty and has no more notes than were sent. Otherwise, or on any `ServiceError` or defect, the service logs a warning and keeps the raw notes, and the request succeeds. This is the same code path as [Customer Book's compaction](customer-book.md#notes-compaction): the shared `note-compaction-*` config with no new keys, and no processing message sent. Candidate notes and `infoNotes` are never sent.
4. **Duplicates** (every source, over the single or merged extract): `computeCatalogueItemNameCounts` (`Map[CatalogueItemName, Int]` over defined names, exact and case-sensitive, mirroring `uq_catalogue_item_name (organization_id, name)`) and `computeCatalogueItemVariantSkuCounts` (`Map[String, Int]` keyed on `sku.value.toLowerCase(Locale.ROOT)` over every variant of every candidate, mirroring `uq_catalogue_item_variant_sku (organization_id, lower(sku))`). Both are passed into the per-candidate field computation, which marks a value whose count is above one. Nameless candidates and absent SKUs are never counted. Two variants of the same candidate can both be duplicates. Nothing is compared with stored items, merged or reordered, and no repository call is made. **Residual risk (follow-up 10):** `Locale.ROOT` applies context-sensitive and full mappings, while PostgreSQL `lower()` under a libc collation maps one character at a time. The two can disagree: `ΟΔΟΣ` lowers to `οδος` in Java (final sigma) but to `οδοσ` in PostgreSQL, and `İ` lowers to two characters in Java. The preview can therefore miss a SKU duplicate that the add flow then rejects with 409. The user chose to keep `Locale.ROOT`.
5. **Field computation** (pure `compute...` functions over the AI values, before the Chimney mapping): `inferredFields`, `missingFields` and `duplicateFields` per the path table. `needsAttention = missingFields.nonEmpty || duplicateFields.nonEmpty`.
6. **Notes.** A candidate's `extractionNotes` are its AI notes followed by each variant's AI notes in variant order, unprefixed. The service writes no candidate notes. Top-level `extractionNotes` are the AI's, compacted per step 3.
7. **Mapping** (Chimney, inline, no private mapping helpers): `catalogueItemAIExtract.into[CatalogueItemCandidate]`, with every variant's attributes mapped through `.withFieldComputedFrom(_.variants.everyItem)(_.variants.everyItem.attributes, _.attributes.map(...).toMap)` (the last entry wins for repeated names). The price derives automatically, and `currencyInferred` / `sellingUnitInferred` are dropped as extra source fields. The computed lists and attention are bound with `.withFieldConst`. Every candidate the AI returns is mapped. An all-empty nameless candidate would show `/name` and `/variants` as missing, because the "otherwise unidentified" rule lives in the prompts only.
8. **`infoNotes`**: `Processed <entriesProcessed> of <entriesIdentified> entries`; then `Catalogue items created <n>` only when `candidates.size` differs from `entriesProcessed`; then `Item variants created <v>` only when `v` differs from `candidates.size`, where `v` counts each candidate as its variant count but at least 1 (a candidate with no variants adds 1), so the line appears only when some item has two or more variants; then `Empty rows (<n>) at [<rows>]` and `Unidentified rows (<n>) at [<rows>]` only when non-empty, in that order. This is Customer Book's `computeInfoNotes` shape with a catalogue-specific item line and an added variants line.
9. No `ImageProcessing`, S3 or repository call for any source. Nothing is stored.

### PDF extraction

**Status: shipped in issue 607; `.pdf` is accepted by `aiExtract`.** Still open: the user-run session of the Catalogue golden check ([acceptance gap 17](../acceptance-test-gaps.md#17-catalogue-extraction-prompts-and-note-compaction)). [Epic](../../pages/epics/06-catalogue.md) scenarios 30–31 and requirements 1 and 11 define the product contract. Customer Book extraction accepts PDF too through the shared `aiExtractData` list (follow-up 17, done; see [Customer Book PDF extraction](customer-book.md#pdf-extraction)).

- **Media types.** `SupportedMediaType.PDF` has extension `pdf` and MIME `application/pdf`, in the group `pdfs`. `aiExtractData = images ++ pdfs ++ spreadsheets` is scanned by Catalogue `aiExtract` and, since the Customer Book PDF round merged the former Catalogue-only `extractCatalogueData` into it (user decision), by Customer Book too. `images` (item image upload, organization logo) is unchanged, so the image-upload route still refuses `.pdf`. Extension matching stays case-insensitive.
- **Content check (user decision: content plus name hint, as for every type).** A PDF goes through the same single `tika.detect(inputStream, fileNameDeclared)` call as images and spreadsheets, and the result must be `application/pdf`. `FileScanner` has no PDF branch and no fallback of its own. When Tika recognises the content as another type, the content wins: PNG or JPEG bytes named `.pdf` get `400` "does not match" and are never sent to the AI (epic scenario 17). **Accepted trade-off:** when Tika's content detection finds no specific type, Tika uses the name hint. This was observed (issue 607 PDF round, not kept as a test) for binary bytes with no signature Tika recognises, such as `00 01 02 03 FE FF`: named `.pdf`, they pass the scan and reach the AI, and the provider's rejection then gives `500` (epic scenario 31). Text-like bytes may instead be detected as a text type and get `400`; that case is not pinned by a test. This mirrors Customer Book's accepted OOXML trade-off, where POI is the structural backstop.
- **Dispatch.** A PDF goes to `aiClientDataExtraction.extractFromPdf[CatalogueFileAIExtract](path, catalogueFileExtractFileName.value, AIInstructions.extractCatalogueItemsFromPdfInstructions, processingMessageOpt)`. The uploaded file name is sent to OpenAI unchanged as the PDF's file name (user decision); it is not stored by us, and `store: false` keeps OpenAI from storing the request. Like an image: one request for the whole document, no merge, no compaction, the same duplicate, field, notes, mapping and `infoNotes` steps. There is no PDF library, page count or pre-check.
- **AI client.** `extractFromPdf` calls the OpenAI Responses API (`/v1/responses`, sttp-ai `createModelResponse`), because chat completions has no file input. See [External client: OpenAI Responses endpoint](../project/external-client.md#openai-responses-endpoint). Since the issue 607 migration, images, PDFs, spreadsheets and note compaction use that endpoint through one shared send-and-decode function; `extractFromPdf` is built and covered by `AIClientDataExtractionSpec`, and `aiExtract` dispatches PDFs to it. It uses its own `pdf-model` (default `gpt-6.1-sol`, env `AI_CLIENT_DATA_EXTRACTION_PDF_MODEL`) and `pdf-reasoning-effort` (default `medium`, env `AI_CLIENT_DATA_EXTRACTION_PDF_REASONING_EFFORT`), the same values as the image settings but separately configurable (user request), and the shared `request-timeout`. The new variables are optional with defaults, so no Terraform change is needed. The configured PDF model must accept PDF input; only the live golden proves that. Every request sends `store: false` (user decision), so OpenAI keeps no stored copy of the file or the extracted answer.
- **Failures.** A provider refusal of a locked, damaged or too-long (about 100 pages) PDF, an error status, an exhausted timeout, a model refusal, an `incomplete` response or output that breaks the strict schema all become `UnexpectedError`, so `500 INTERNAL_SERVER_ERROR` with no partial result. Timeouts and 408/409/429/5xx are retried as for images, so a PDF that never completes takes up to three `request-timeout` attempts (about 9 minutes with the defaults) before the 500.
- **Prompt (built, issue 607 slice 5).** `extractCatalogueItemsFromPdfInstructions` and `extractCatalogueItemsFromImageInstructions` are both built by the private `extractCatalogueItemsFromVisualSourceInstructions(sourceDescription, sourceName, sourceReadingRules, entryPositionsRule)`, the last member of `AIInstructions`. The image call passes `"an image"`, `"image"`, no reading rules and its original positions bullet; its text is byte-identical to the pre-template prompt (verified once by a before/after dump with `cmp` and SHA-256 `b9f65267…`, no test kept). The template is a `raw"""…"""` string because the image prompt contains a literal `\"OILS\"` that an `s` interpolator would unescape; a literal `$` in the template must be written `$$`. The PDF call passes `"a PDF document of one or more pages, typed or scanned,"` and `"document"` (so every "image" reference reads "document"), plus a reading paragraph: read the pages in page order as one continuous source; an item may continue onto the next page and stays one item; page headers, footers and page numbers repeated across pages are not entries and count nowhere, with one left-out note per such repeated line rather than one per page (the same no-repeated-notes intent as the spreadsheet note combining). Its positions bullet: `emptyEntryRows` is always `[]`, and positions are numbered from 1 top to bottom on each page, in page order, straight through all pages (the 3rd entry on page 2 after 20 on page 1 is 23). The processing message applies as for an image. It keeps the `Return exactly one CatalogueFileAIExtract JSON object` phrase. Image, CSV and PDF requests all go to `/v1/responses`, so the existing Catalogue acceptance stubs would also answer a PDF request: the PDF acceptance stub must additionally match `input_file` at a higher priority.
- **Memory.** The whole file is read and base64-encoded in memory, as for images: 20 MB becomes about 27 MB of request body.
- **Tests.** Built: `FileScannerSpec`: a real PDF and a `.PDF` name are accepted; PNG bytes named `.pdf` are a mismatch. No test pins Tika's name fallback for unidentifiable bytes; it is Tika's behaviour, not ours. `CatalogueFileServiceSpec`: PDF dispatch without guidance (declared name `catalogue-price-list.pdf` passed unchanged, whole response with `Processed 0 of 1 entries`/`Unidentified rows (1) at [23]`, raw notes kept, no spreadsheet or compaction call) and with guidance, and PDF AI-failure propagation. `AIClientDataExtractionSpec`: the sent Responses body, success, and the failure and retry cases. `CatalogueFileApiSpec`: a PDF success and JPEG bytes named `.pdf` rejected with `400`; the extraction "unsupported extension" case moved from `.pdf` to `.gif`. `CustomerBookFileApiSpec`'s `.pdf` unsupported case, unchanged, proves CB still refuses PDF. Manual goldens (user-run, see [Manual AI golden checks](#manual-ai-golden-checks)): `golden/CatalogueFileAiExtractGoldenSpec` (issue 607 rework, agreed, not built; today still `golden/CatalogueFileAiExtractFromPdfGoldenSpec` and `golden/CatalogueFileAiExtractUnrelatedContentGoldenSpec`) on `pdf-1.pdf` declared as `Catalogue-Price-List.PDF`, and on unrelated image, CSV and PDF assets.

### Instructions

The three Catalogue extraction prompts (image, PDF, which shares the image template, and file) follow the shared [prompt structure](../standards/ai-extraction.md#default-instructions-and-user-guidance) and describe the new AI shape exactly. The unit, price, currency, attribute, grouping, transcription and note-style rules carry over in substance. What changes:

- **No duplicate or issue rules.** The duplicate comparisons and the four issue flags are removed, along with the fixed-warning list. The prompts state only that the server computes duplicates, missing fields, attention and counts. Notes never restate which field is missing, inferred or duplicated.
- **Validated values (issue 607, user decision; image, PDF and file prompts alike).** [General rule](../standards/ai-extraction.md). A price amount, and every number of a selling unit, must pass validation later, so it is returned only when every digit is clearly readable. A price with any digit smudged, overwritten, under glare, cut off or uncertain is `price: null` with a short variant note such as `Price could not be fully read`, never a partial or guessed amount; a selling unit with such a number is left out with a short note. This replaces the earlier most-plausible-reading rule for a partly unclear price amount.
- **Names.** `name` is `null` when no item name is readable, never invented. An entry with no readable name is still returned as a candidate when any other detail is readable (description, SKU, label, variant description, attribute, price amount or selling unit) and it does not continue a named item in the same image or batch. An entry with content but no readable detail goes to `unidentifiedEntryRows`. Wiped-out text (crossed out, struck through, scribbled over or wiped) was removed on purpose by the writer and is never read as a value, and a smudged or cut-off detail is not usable either, so an entry whose only content is wiped out, smudged or cut off is not a candidate and goes to `unidentifiedEntryRows` too; an entry that still has one readable detail from the list above (such as a price amount, selling unit or SKU) stays a candidate ([general rule](../standards/ai-extraction.md); issue 607, user decision, after the Customer Book v5 image measurement returned a crossed-out entry as a customer). A nameless row at the start of a batch that would have continued an item in the previous batch becomes its own nameless candidate (follow-up 13).
- **Free text copied exactly as printed (issue 607 exact-copy round; built in the image, PDF and file prompts).** [Epic step 10](../../pages/epics/06-catalogue.md), scenarios 33–35 and requirement 19. Applies to the image, PDF and file prompts alike, and to `name`, the item `description`, and each variant's `sku`, `label`, `description` and every attribute `name` and `value`. The returned value is the source text as printed: never corrected, completed, expanded, translated, re-cased, re-punctuated or re-quoted, and never replaced with a more likely word or code. Only four changes are allowed: leading and trailing spaces are removed, the commas, semicolons and full stops that only separate or end the printed text are dropped, text printed over several lines is joined with one space, and repeated spaces inside the text become one. A full stop printed as part of a word (an abbreviation or initial, such as `No.`, `approx.` or `St.`) stays, and punctuation that is not printed is never added, so `Olive oil.` gives `Olive oil` and `Olive oil 1L` stays `Olive oil 1L`; prices, quantities and units are not free text and are unaffected ([general rule](../standards/ai-extraction.md); issue 607, user decision, extended from Customer Book after its v5 image measurement flipped a printed `Ltd` to `Ltd.` and kept a sentence-ending full stop). A value longer than 255 characters (the `NonEmptyTrimmed` limit shared by all seven fields) keeps its first 255 characters exactly as printed, without a trailing space, with one note at its narrowest scope naming the field, such as `Description was too long and was cut` (user decision). Quotes (curly or straight), letter case, accents, abbreviations such as `Φρεσκ.`, punctuation and alphabet are kept. A clearly printed value that looks misspelt (scenario 33's `Πάρκαπα`) is returned as printed, with one short note at its narrowest scope, such as `Name may be misspelled in the source` on the item or `Label may be misspelled in the source` on the variant, and no suggested correction. When part of a value cannot be made out, only the visible characters are returned, never a different or more likely word or code, with one note naming the detail, such as `Name partly unclear, please check`, and no suggested reading. An attribute whose name or value cannot be seen at all is left out, with one note on the variant, because attribute names and values are never null or empty. Neither note adds a field-list entry or changes `needsAttention` (requirement 8). Both are item or variant notes, never top-level, so the compaction prompt is not involved. The interpretation rules (closest supported value, abbreviations, translations, OCR variations, obvious typing errors) turn source wording into a supported selling unit or currency only (requirement 6) and never rewrite free text. A correction the processing message asks for is a followed instruction and gets no note (requirements 3 and 17), still within the no-invented-facts limit. A line ending in a hyphen is joined with no space and the hyphen is kept (`Extra-` and `virgin` give `Extra-virgin`), and a run of spaces or tabs counts as repeated spaces. The processing message may ask for any rewording that uses only what the source shows (spelling, case, abbreviations, translation); it is applied with no note and no misspelt note on the reworded value. Agreed exceptions (user decisions): a meaningful column with no usable label is still named as an attribute from its values, and price is not free text. A partly unclear price amount used to keep its most plausible reading with a note; that exception was replaced by the validated-values rule below (issue 607, user decision). No response, schema, codec or service change: enforcement is prompt-only and the service does not normalize text (user decision). Before this round the visual template told the model to interpret "OCR variations" in all source text, kept only item names "as written", and, like the file prompt, used "the most plausible reading" of a partly unclear SKU, label, description or price and noted the assumption; the prompts now limit that interpretation to the selling unit and currency and keep the most-plausible-reading rule only for a price amount. Proof is the user-run image golden, which compares every value exactly, notes excluded, with the hand-corrected golden files ([Manual AI golden checks](#manual-ai-golden-checks)); no automated test can assert model output, and the standard forbids prompt-prose tests.
- **Kept values.** A variant whose selling unit cannot be settled is kept with `sellingUnit: null`. A readable amount whose currency cannot be settled is kept with `currency: null`. Either gets a note only when a unit or currency is visible but cannot be read or matched to a supported value; a simply blank unit or currency cell gets no note, because `missingFields` already reports it (epic requirement 12). Only a price whose amount cannot be read is `null`, with a note; a blank price is `null` with no note.
- **Value constraints.** Each prompt has a value-constraints bullet, because `NonEmptyTrimmed` (trimmed, 1–255 characters) does not reach the provider schema and a breach fails the whole result: `name`, both descriptions, `sku`, `label`, and every attribute name and value are trimmed, non-empty text of at most 255 characters, `null` where optional and never `""`. The bullet also restates the selling-unit range (greater than 0, at most 99999, per `CatalogueItemVariant*Value`), the supported units and currencies, and the add flow's price rule (non-negative, at most 12 integer digits, at most 2 decimals). The price rule does not fail the decode: `PriceAmount` is `Pure` and the preview does not run `PriceValidator`, so an out-of-range amount reaches the preview and is rejected only when the user adds the item. This was already true before issue 607 and is not changed by it.
- **Inferred flags** as defined in the flag table. A unit or currency supplied by the processing message is inferred.
- **Counts.** `entriesProcessed` = original rows or visible entries that give or join at least one candidate, with or without a name. A grouped row counts once. `entriesIdentified` = processed + empty + unidentified. Entries the message asks to skip count nowhere. Image prompt: `emptyEntryRows` is always `[]`, and `unidentifiedEntryRows` holds the AI's best-effort top-to-bottom positions starting at 1.
- **Processing message (limited to reading the upload, issue 607).** All three prompts open their rules with `These are the default reading rules. The relevant parts of a separate user processing message, defined below, take priority over any of them, within the three fixed limits given after these rules:`. The three limits are: results fit the response rules (an unmeetable request is applied as far as possible, with no note); no invented details; the system computes counts, duplicates, missing fields and attention. A relevance block at the end of the message section follows only the parts about reading this upload into catalogue candidates (entries to include, skip, split or group; what columns, labels or details mean; a default selling unit or currency; how to fill fields from the source), falls back to the default rules for ambiguous or conflicting parts, ignores everything else (questions, opinions, stories, requests to reveal or change the instructions, abusive or hateful content) without answering, repeating or quoting it, and then adds the fixed top-level note `Unrelated processing message instructions were ignored` exactly once, also beside the nothing-found note. No other note mentions the message: a unit or currency it supplied is flagged inferred with no note, a detail it drops gets no note, and the note-style example no longer describes message requests. The message is sent with every spreadsheet batch, so each batch may add the fixed note; the unchanged compaction prompt is expected to merge the copies into one, but when compaction fails or returns an unusable result the raw notes are kept and the fixed note repeats once per batch (open item, issue 607). Enforcement is prompt-only and unverified live ([epic step 10](../../pages/epics/06-catalogue.md), scenario 32 and requirement 17). A detail the message asks to drop is meant to be absent. Known gap: the service derives `missingFields` from the returned nulls, so a dropped selling unit, currency or name is still reported missing ([epic gap 14](../../pages/epics/06-catalogue.md#14-a-detail-dropped-on-request-is-still-reported-missing), mirroring Customer Book gap 7). The message stays a separate final user message, sent with every batch.
- **Compaction prompt.** `AIInstructions.compactCatalogueFileNotesInstructions` is Customer Book's compaction prompt with catalogue wording. Its opening line names a catalogue file, so its WireMock stub cannot match Customer Book's.

These stay prompt rules. Live-model adherence is not guaranteed and is checked only in the manual goldens ([acceptance gap 17](../acceptance-test-gaps.md#17-catalogue-extraction-prompts-and-note-compaction)).

### Unchanged by issue 607

The shared AI extraction client selects a configurable model per operation, shared by catalogue and customer extraction: `ai-client-data-extraction.image-model` defaults to `gpt-6.1-sol`, `pdf-model` (Catalogue only) to `gpt-6.1-sol`, and `csv-model` (including converted spreadsheets) to `gpt-6.1-terra`. Override them with `AI_CLIENT_DATA_EXTRACTION_IMAGE_MODEL`, `AI_CLIENT_DATA_EXTRACTION_PDF_MODEL` and `AI_CLIENT_DATA_EXTRACTION_CSV_MODEL`. Each operation also has a reasoning-effort setting: `image-reasoning-effort` and `pdf-reasoning-effort` default to `medium` and `csv-reasoning-effort` to `low`. Override them with `AI_CLIENT_DATA_EXTRACTION_IMAGE_REASONING_EFFORT`, `AI_CLIENT_DATA_EXTRACTION_PDF_REASONING_EFFORT` and `AI_CLIENT_DATA_EXTRACTION_CSV_REASONING_EFFORT`. The client forwards each configured effort to its operation; use a value supported by the selected model. Protocol tests and WireMock request matchers do not pin model names. Live quality and latency after a model override require manual verification.

`AIClientDataExtraction` keeps its timeout, retry and error policy. A failed primary batch fails the request without a partial result. Spreadsheet batches are at most `ai-client-data-extraction.csv-batch-max-data-rows` (default 100) rows, with up to `csv-batch-parallelism` (default 4) concurrent requests and original row numbers. Both settings are shared with Customer Book. AI grouping and continuation linking use only the batch's own context, and nothing is merged or reattached across batch boundaries (follow-up 13). Row lists use `Row Number` = the record's position in the parsed stream (header = 1). That is the file position only while every row is physically present: commons-csv `CSVFormat.DEFAULT` skips truly empty CSV lines (`,,,` lines are kept as blank rows), and Apache POI's `rowIterator` skips Excel rows that are not stored, which is how Excel normally saves an empty row. Such rows are then never reported as empty, and every later row number is lower than the real one (follow-up 16; known from the library defaults, not yet proven by a test). Strict structured output (`strict: true`), attribute entries as closed name/value arrays, last-wins attribute conversion, first sheet only and `.xls` support are unchanged. Reuse `FileScannerSpec`/`SpreadsheetToolSpec` for media and size boundaries. Do not add an over-cap real-HTTP test while the transport hang remains open.

## Known issues, edge cases, and larger follow-ups

These describe current behavior, not proposed requirements already implemented.

1. **Missing-resource error semantics:** detail GET and image upload return 500 for missing/archived/foreign targets. Updates/archive return successful no-ops for an unavailable parent. Invalid existing-variant references fail the whole update with 500. Non-member access also returns 500 through shared authorization. A consistent 4xx policy requires an agreed contract/error change across callers and tests.
2. **Repeated variant update IDs:** the validator accepts repeated IDs; the repository compares distinct loaded rows with input length, so even identical entries produce 500 and rollback. Prefer explicit duplicate-ID validation if this error contract is changed; do not silently pick one update.
3. **Selling-unit precision exceeds storage:** a compact value such as `1E-20000` satisfies the agreed positive/max rule but may fail JSONB numeric persistence/encoding. PostgreSQL [JSONB numeric restrictions](https://www.postgresql.org/docs/17/datatype-json.html) apply after validation. This is a domain/internal-caller example: the current HTTP decoder rejects this exponent before validation (issue 12). The domain rule deliberately has no storage-derived precision limit. Supporting every accepted domain value end to end needs a representation decision; do not silently restrict validation.
4. **Image writes are not atomic:** the pre-read does not lock the item across scanning/S3. An archive can commit after the read; upload then writes objects and the final database update no-ops successfully. A second S3 write or database failure can leave changed objects; concurrent uploads can interleave the original/normalized objects at fixed keys. Consider versioned object keys, a conditional database association, and compensation/cleanup as one separately designed change.
5. **Oversized upload can stall:** real HTTP beyond the entity limit can hang instead of failing promptly. Reproduction and prevention: [known issue](../known-issues.md#oversized-tapir-upload-can-hang-the-request-instead-of-failing-fast). Do not add the destabilizing end-to-end test until transport behavior is fixed.
6. **Large requests and results:** summary-all returns all eligible items and variants and signs populated images sequentially. Validators have no count caps, but the default Smithy4s decoder rejects arrays/maps over 1,024 entries before validation. Batch nesting can still exceed the [PostgreSQL parameter ceiling](https://www.postgresql.org/docs/17/limits.html) of 65,535: INSERT binds 14 parameters per variant across the whole batch, so 4,682 total variants exceed it (for example, several items with fewer than 1,024 variants each), even when compact JSON fits the body cap. UPDATE binds 10 per variant plus two scope IDs; its 6,554-row SQL ceiling is currently unreachable through one HTTP list but remains relevant to internal callers. Database failure rolls back the operation and returns 500. These thresholds derive from pinned decoder source and SQL construction, not a completed large-request HTTP reproduction. Consider transactional chunking plus explicit request limits; pagination/workload limits are separate product decisions.
7. **Stored-data assumptions:** an item without a non-archived child is hidden by joined reads; application creation/archive transactions prevent this, but no cross-table database constraint enforces it. Native SQL/manual data changes must preserve this invariant and validated JSON. The testing join also cannot expose a parent with zero total variants.
8. **Deployment conversion:** editing the init migration does not upgrade an existing database. Before deployment over retained data, design an append-only conversion for item/variant data, statuses/archive flags, currency values and case-insensitive SKU collisions. Disposable-database verification is not migration proof.

9. **Database-incompatible text:** `NonEmptyTrimmed` accepts an interior U+0000 (for example `a\u0000b`), but PostgreSQL text/JSONB cannot store it. A typed request can pass validation and fail persistence with 500. A shared database-safe text rule needs review across the other features using this predicate; do not add an isolated Catalogue normalization. See [PostgreSQL JSON string restrictions](https://www.postgresql.org/docs/17/datatype-json.html).
10. **Unicode SKU comparison:** lookup and index agree on database `lower(sku)`, which uses the configured [collation](https://www.postgresql.org/docs/17/collation.html). This is not full Unicode caseless matching: `straße` and `STRASSE` can remain distinct. Current tests prove ASCII case-insensitive SKUs. Define the supported alphabet/collation or a normalization strategy before promising broader equivalence; changing it requires an index/data migration. Extraction's SKU duplicate check (since issue 607) uses `toLowerCase(Locale.ROOT)`, by the user's choice. That is not always the database's `lower()`: Java applies the final-sigma rule (`ΟΔΟΣ` becomes `οδος`, PostgreSQL gives `οδοσ`) and maps `İ` to two characters. A preview can therefore miss a duplicate that the add flow rejects with 409. This is accepted residual risk under [Catalogue gap 8](../../pages/epics/06-catalogue.md#8-sku-case-comparison-does-not-cover-every-unicode-case-equivalence).

11. **SKU swaps/transfers:** the partial expression unique index checks changes immediately. Swapping existing live SKUs A/B in one `variantsUpdate` can return 409 even though the final state would be unique; the whole transaction rolls back. A transfer that clears the old owner in the same statement can also depend on write order. Supporting this needs a deliberate write strategy (for example, coordinated two-phase clearing/reassignment) or a normalized stored key/constraint redesign, with concurrency tests.

12. **JSON decimal precision — accepted limitation:** Smithy4s request decoding, the selling-unit JSONB codec, and the typed acceptance client's default decimal codecs use DECIMAL128 (34 significant digits), a 308-digit limit and an absolute-scale limit of 6,178. Therefore `0.12345678901234567890123456789012346` can become `0.1234567890123456789012345678901235` during request or database decoding; larger representations can fail decoding. A later unrelated variant update can persist a value rounded during its database read. Validator-level exactness does not prove exact input or readback. The user accepted this limitation because business values are not expected to approach this precision; keep the default codec and defer precision changes/tests until that expectation changes. Current prices fit within 34 significant digits. If revisited, assess persistence, the transport compiler/library integration and acceptance-client codecs together, with independent exact read/update and typed HTTP regressions. The pinned Smithy `JsoniterCodecCompiler` exposes no numeric-precision setting.

13. **Cross-batch catalogue grouping — deferred:** one item can span independent 100-row AI batches. Its variants may appear as separate candidates. Today a variant-only continuation without a named-item association in its batch can remain unidentified. Since issue 607, such a row with any readable detail comes back as its own nameless candidate with `/name` in `missingFields` (user decision, 2026-11-14). Aggregation preserves separate candidates and upload-wide duplicate reporting; it does not reconstruct a single item or adjust processed counts for a cross-batch merge. The user explicitly deferred this case. Revisit source-row/column-value evidence, verification against source records, and deterministic reconciliation together. The earlier target was to merge named candidates only with an explicit shared item key/grouping marker and attach a variant-only continuation to the preceding item with a review note, without another AI reconciliation pass. AI source-reference fields and their schema were withdrawn until this work resumes. Product limitation: [Catalogue gap 12](../../pages/epics/06-catalogue.md#12-one-item-can-be-split-between-extraction-batches).

14. **AI metadata validation — explicitly deferred:** counts and row findings remain AI-reported, with batch sums/concatenation only. Counts are not checked against candidate totals, and row findings are not checked for valid positions, overlap, or correspondence with source records. Inconsistent metadata does not introduce a new extraction failure. Revisit validation and its failure policy together if this work resumes.

15. **Uniqueness self-exclusion — deferred to the next PR:** `CatalogueItemUniquenessGet` accepts only optional `name`/`sku`, so checking an existing item's unchanged name or a variant's unchanged SKU reports it as taken by that same record. Add optional `catalogueItemID` for the name check and optional `catalogueItemVariantID` for the SKU check, excluding only the corresponding record within the organization. Creation checks omit both IDs. Preserve non-archived filtering, case-sensitive name equality, case-insensitive SKU equality, supplied-field response semantics and write-time uniqueness enforcement. Update the contract, validated request, service/repository/query mappings, client and unit/functional/repository/HTTP coverage together. This is planned work, not implemented in the Customer Book refactor. Product limitation: [Catalogue gap 13](../../pages/epics/06-catalogue.md#13-availability-checks-count-the-record-being-edited).

16. **Spreadsheet row numbers after skipped rows — open:** `SpreadsheetTool` and `AIClientDataExtraction.extractFromCsv` number records by stream position, while commons-csv skips truly empty CSV lines and POI skips unstored Excel rows. A real Excel file with empty rows therefore reports no empty rows and shifted row numbers in `Empty rows`/`Unidentified rows` and in the AI's notes. Shared with Customer Book. Not raised by issue 607; found while specifying the realistic golden fixtures (2026-11-15). Fixing it means numbering from the source row (`CSVRecord.getRecordNumber` with empty lines kept, `Row.getRowNum() + 1` for Excel) with `SpreadsheetToolSpec`/`AIClientDataExtractionSpec` proof.

17. **Customer Book PDF extraction — done (issue 607, brief in `7909c42d`):** the Customer Book PDF round reuses `extractFromPdf` with its own Customer Book PDF prompt and tests, and merged `extractCatalogueData` into the shared `aiExtractData` (user decision), so Customer Book accepts `.pdf`; Catalogue behaviour is unchanged. Its live golden session is tracked in [gap 14](../acceptance-test-gaps.md#14-address-note-and-processing-message-rules-in-customer-extraction). See [Customer Book PDF extraction](customer-book.md#pdf-extraction).

Exact decimals remain JSON numbers. Clients that parse them as binary floating point can lose precision; switching to string encoding is an unresolved client-contract decision. A future unarchive feature must resolve live name/SKU collisions; no unarchive behavior is implied here.
