description: PO clarification → user approval → EM assessment and plan → TDD implementation in reviewed slices → EM technical review → PO completeness review
argument-hint: <feature, bug, or issue description>
---

Handle "$ARGUMENTS". The main conversation is the orchestrator: it follows `.agents/contracts/workflow.md`, talks to the user, spawns and resumes `product-owner`, `engineering-manager`, and the selected Lead, relays their `USER_QUESTION`s, runs the gates, and commits approved slices. It makes no product or technical judgement of its own — product belongs to PO, technical requirements, plan, and review belong to EM.

Every role, at every stage: read `AGENTS.md` and the `agent-docs/` guides it routes to before acting, ask about every assumption up front instead of deciding, and take no initiative beyond what was agreed. Subagents never stage, commit, or push. After the user explicitly approves the exact current diff, the main conversation stages and commits only that approved slice under `.agents/contracts/workflow.md`; it never pushes.

New features and changes to features that already ship run the same stages and gates. For an existing feature, every stage starts from the epic, the feature doc, and the code that exists, and works as a delta: state it as "today X, after this Y", update the existing epic and feature doc in place instead of creating new ones, and slice the work by kind of edit — update the docs, adapt or add the test, add the new function, change the existing function, migrate the data. Existing tests are adapted only because the user agreed the behavior changes, never to reach green.

1. **Product clarification.** For any new, changed, or unclear product requirement, ask `product-owner` for a `PRODUCT_BRIEF`; relay its `USER_QUESTION` rounds to the user until nothing material is open. Every question you put to the user follows `.agents/contracts/workflow.md` § "Writing a question the user can answer"; rewrite one that falls short, keeping its substance, or send it back if it lacks facts. PO updates the affected epic and any other `pages/` documentation. Use the user's own requirements directly only when the story and its acceptance are already unambiguous.
2. **Gate 1 — user approval and commit.** Put the `PRODUCT_BRIEF` and PO's `pages/` diff to the user for review. After the user explicitly approves that exact diff, stage and commit only the approved `pages/` slice. Do not begin technical work before the commit succeeds.
3. **Technical assessment.** Spawn `engineering-manager` with the approved `PRODUCT_BRIEF` (or the user's requirements), the committed `pages/` diff, and the user decisions so far. Keep that session for the whole feature. EM returns `TECHNICAL_REQUIREMENTS` — the technical rules and constraints the brief implies but PO did not state — plus its concerns with recommendations. Relay its `USER_QUESTION` rounds in that format, unchanged in substance, and resume the same EM with each answer until nothing material is open; send product questions it raises to PO first.
4. **Plan and complexity.** Resume EM to update the engineering docs it owns and return `ENGINEERING_PLAN` (approach, paths, pitfalls, ordered slices of at most 3 files each with the first = interfaces and failing tests, required checks, `MEDIUM` or `HIGH` per `.agents/contracts/complexity.md` with a one-line reason) and a ready `ENGINEERING_HANDOFF`.
5. **Gate 2 — user approval and commit.** Put the plan, tier, and EM's exact engineering-doc diff to the user. After explicit approval, stage and commit only that approved slice before any code is written.
6. **Dispatch.** Spawn `lead-engineer-medium` or `lead-engineer-high` per the approved tier with EM's `ENGINEERING_HANDOFF`, unchanged.
7. **Slice loop.** The Lead first returns its open assumptions and questions; resume EM with them and pass EM's `LEAD_ANSWERS` back, putting any `USER_QUESTION` to the user first. The Lead then returns the skeleton slice (interfaces, signatures, failing tests, real red evidence) and stops. Resume EM with the `SLICE_REPORT`; EM reviews the real diff and returns `SLICE_ASSESSMENT`. Send findings back to the same Lead until EM marks the slice ready, then present the diff and EM's assessment to the user. After the user explicitly approves that exact diff, stage and commit only that slice, then resume the same Lead. Repeat for every implementation slice: at most 3 hand-written files, real check results, stop, EM review, user approval, commit, resume. Never let the Lead run ahead, and never approve a slice yourself.
8. **Technical completion review.** Resume EM with the Lead's final `IMPLEMENTATION_REPORT`. EM reviews the cumulative diff, the docs, and the evidence against its technical requirements, the plan, and the standards, and returns `TECHNICAL_REVIEW`. Route findings to the same Lead until EM reports passed; EM fixes trivial factual docs itself.
9. **Product completion review.** Resume `product-owner` with EM's delivered-behavior, documentation, and test-to-requirement handoff. It returns `PRODUCT_ACCEPTANCE` — complete, or the gaps. Resume EM with it; EM routes each gap to its owner: missing behavior or coverage to the same Lead as another approved slice, docs or technical debt to itself, an uncaptured requirement back to the user as a new round.
10. **Close.** Resume EM for its `CLOSE_REPORT` and present it: delivered behavior, checks actually run, docs updated, PO's acceptance, and any gap or verification left open.

If `engineering-manager` or a Lead cannot be spawned, stop and tell the user; do not do their stage in the main conversation. Use task tracking when the slice list is long.
